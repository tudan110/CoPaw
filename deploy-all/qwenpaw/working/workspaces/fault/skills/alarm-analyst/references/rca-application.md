# 应用层故障根因分析（9场景）

> 本文档含两类互补视角：**应用自身视角**（场景 1–4：代码缺陷/业务逻辑/依赖服务/API 接口，从应用内部下钻）与**拨测/用户侧感知视角**（场景 5–9：以应用拨测/RUM 感知入口异常，自顶向下沿"网络→接入→IaaS→PaaS→应用自身"分层下钻 + 排除法定位）。已知是应用进程/代码问题时用前者；"入口不可用/变慢"但根因层次未知时用后者。

## 1. 代码缺陷

**故障现象**：应用服务异常退出、内存持续增长、响应延迟逐渐升高，业务处理异常或服务不可用。

**根因类型**：
- 内存泄漏（对象未释放、缓存未清理、资源未关闭）
- 线程死锁（多线程竞争、锁顺序不一致）
- 空指针异常（未判空、并发访问共享对象）
- 资源未释放（连接未关闭、文件句柄未关闭）
- 并发竞争（数据竞争、计数器错误）

**分析步骤**：
1. **告警识别**：接收应用层异常告警（服务不可用、错误率升高、响应延迟超过阈值），或应用日志中的异常堆栈信息（NullPointerException、OutOfMemoryError等）。
2. **拓扑关联**：通过应用拓扑确认异常服务的上下游依赖关系；检查是否为单个服务问题还是多个服务同时受影响。
3. **性能指标分析**：查看应用的CPU使用率、内存使用率、GC频率和耗时、线程池状态、请求队列长度等性能指标。
4. **根因判定**：
   - 内存使用率持续增长且GC无法回收 → 内存泄漏
   - 线程池活跃数达到上限且请求排队 → 线程死锁
   - 日志中频繁出现NullPointerException → 空指针异常
   - 连接数持续增长且不释放 → 资源未释放
   - 计数器值异常且并发访问时出现 → 并发竞争
5. **影响评估**：结合应用拓扑和业务指标，评估代码缺陷影响的业务范围和程度。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：伴随近期发布 → 立即回滚版本；内存泄漏/死锁致服务劣化 → 滚动重启异常实例、扩副本转移流量、限流保护；单实例异常 → 摘除该实例保住整体。
- 🔧 **根因处置（修复）**：结合堆栈/堆转储/线程转储修复具体缺陷（补判空、修锁顺序、释放资源/连接、修并发竞争），补充压测与代码评审后再发布。
- 🧭 **影响范围决策**：核心业务受影响 → 先回滚/重启/摘除恢复可用，再离线分析定位缺陷；影响小可保留现场（dump）后再处理，便于根因取证。

## 2. 业务逻辑异常

**故障现象**：业务处理结果与预期不符、数据不一致、事务回滚异常，但服务本身可能正常响应。

**根因类型**：
- 状态机错误（业务状态转换逻辑异常）
- 数据一致性破坏（分布式事务失败、最终一致性问题）
- 幂等性失效（重复请求导致数据重复处理）
- 事务回滚失败（补偿事务未正确执行、回滚不完整）

**分析步骤**：
1. **告警识别**：接收业务监控告警（业务处理失败率升高、数据一致性检查失败、事务回滚异常等），或应用日志中的业务异常信息。
2. **拓扑关联**：通过应用拓扑确认异常业务涉及的服务链路；检查是否有多个服务同时报告数据不一致。
3. **性能指标分析**：查看业务处理成功率、事务失败率、数据一致性检查结果等指标。
4. **根因判定**：
   - 业务状态转换与预期不符且日志显示状态机异常 → 状态机错误
   - 分布式事务失败且数据不一致 → 数据一致性破坏
   - 重复请求导致数据重复处理 → 幂等性失效
   - 补偿事务未正确执行 → 事务回滚失败
5. **影响评估**：结合应用拓扑和业务指标，评估业务逻辑异常影响的业务范围和程度。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：数据不一致/重复处理 → 立即暂停相关业务入口/关闭异常任务防止错误扩大、冻结受影响数据；越权 → 紧急收敛权限。
- 🔧 **根因处置（修复）**：修复代码缺陷（幂等/一致性/权限）、数据对账修复、补偿或回滚错误数据。
- 🧭 **影响范围决策**：涉及资金/数据正确性 → 先止损（暂停入口、冻结数据）防扩大，再修复与对账；影响小可灰度修复。

## 3. 依赖服务故障

**故障现象**：下游服务超时或不可用，本服务调用链路受影响，业务功能降级或中断。

**根因类型**：
- 下游超时（下游服务响应变慢导致调用链路超时）
- 第三方API异常（第三方服务不可用、接口变更）
- 服务降级（依赖服务部分功能不可用，触发降级策略）
- 熔断触发（下游服务错误率超过熔断阈值）

**分析步骤**：
1. **告警识别**：接收应用层服务调用失败告警、熔断器触发告警、或下游服务不可用告警。
2. **拓扑关联**：通过应用拓扑确认异常服务的下游依赖链路；检查是否有多个上游服务同时受到同一下游服务影响。
3. **性能指标分析**：查看服务调用链路的响应延迟、错误率、调用成功率等指标；检查下游服务的健康状态和性能指标。
4. **根因判定**：
   - 下游服务响应延迟升高且本服务超时 → 下游超时
   - 第三方服务不可用且无其他内部告警 → 第三方API异常
   - 下游部分功能不可用且触发降级策略 → 服务降级
   - 熔断器触发且下游错误率超过阈值 → 熔断触发
5. **影响评估**：结合应用拓扑和业务指标，评估依赖服务故障影响的业务范围和程度。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：下游/第三方超时、限流或宕机 → 立即熔断降级、切备用渠道（多支付/多短信通道）或备用下游节点、返回兜底或排队，避免拖垮自身。
- 🔧 **根因处置（修复）**：推动下游服务方/供应商协同恢复、优化重试与超时配置、完善多通道容灾与熔断策略。
- 🧭 **影响范围决策**：强依赖故障 → 先熔断降级/切备用通道保自身可用，再推动依赖方恢复；弱依赖可直接降级。

## 4. API与接口故障

**故障现象**：API调用失败率升高、接口超时、参数校验失败、限流拒绝，业务功能异常。

**根因类型**：
- 接口超时（处理时间过长、超时配置不当）
- 参数校验缺失（输入参数未校验导致处理异常）
- 限流拒绝（请求量超过限流配置）
- 序列化异常（数据格式不匹配、版本不兼容）

**分析步骤**：
1. **告警识别**：接收API网关的限流告警、接口错误率阈值告警、或应用日志中的参数校验失败、序列化异常等信息。
2. **拓扑关联**：通过应用拓扑确认异常API的调用方和被调用方；检查是否有多个调用方同时受影响。
3. **性能指标分析**：查看API的响应延迟、错误率、请求量、限流拒绝数等指标。
4. **根因判定**：
   - 接口响应延迟持续升高且超时拒绝增多 → 接口超时
   - 日志显示参数校验失败且错误码为400类 → 参数校验缺失
   - 限流拒绝告警触发且请求量超过限制 → 限流拒绝
   - 序列化异常且数据格式不匹配 → 序列化异常
5. **影响评估**：结合应用拓扑和业务指标，评估API故障影响的业务范围和程度。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：伴随接口/网关近期变更 → 回滚接口版本或网关配置；接口超时 → 临时上调超时/扩容处理资源、对慢接口降级；限流误伤 → 临时上调限流阈值或对核心调用方放行；序列化不兼容 → 回退到兼容版本。
- 🔧 **根因处置（修复）**：优化接口处理耗时与超时配置、补齐参数校验、按容量评估重设限流阈值、统一数据格式与接口版本兼容策略（契约测试）。
- 🧭 **影响范围决策**：多个调用方/核心业务受影响 → 先回滚/调阈值/降级恢复调用成功率，再修接口根因；仅个别调用方受影响可定向沟通后直接修复。

## 5. 应用不可用（拨测探测失败）

**故障现象**：应用拨测连续失败（连接拒绝/超时/HTTP 5xx），业务入口不可访问。

**根因类型**（按下钻层次组织）：
- 【网络】接入链路中断、路由/ACL误拦、DNS解析失败导致不可达
- 【IaaS】承载主机/VM宕机或资源耗尽（OOM/CPU满/磁盘满）
- 【PaaS】强依赖的中间件/数据库/容器不可用（连接拒绝、注册中心丢失、Pod全挂）
- 【接入】负载均衡/反向代理异常（VIP漂移、后端节点全部摘除）
- 【应用自身】应用进程崩溃/未启动/端口未监听

**分析步骤**：
1. **告警识别**：接收应用拨测失败告警；多探测点交叉确认，排除单点拨测自身网络问题。
2. **变更关联**：核查该应用近期是否有发布/配置变更/扩缩容/割接。
3. **拓扑关联**：基于应用拓扑列出接入入口（域名/VIP）、承载主机/VM、依赖的中间件/数据库、关键网络路径。
4. **分层下钻（排除法核心）**：依次检查 网络层（链路/路由/ACL/DNS，见 `rca-network.md`）→ 接入层（LB VIP/后端健康，见 `rca-paas.md` 负载均衡）→ IaaS层（主机宕机/资源耗尽，见 `rca-iaas.md`）→ PaaS层（依赖中间件/库/容器，见 `rca-paas.md`）→ 应用进程（端口监听/进程存活）。
5. **根因判定（自顶向下命中即止）**：
   - 命中网络不可达/DNS失败 → 网络根因
   - 命中LB后端全摘/VIP异常 → 接入/负载均衡根因
   - 命中承载主机宕机/资源耗尽 → IaaS根因
   - 命中依赖中间件/库/容器不可用 → PaaS根因
   - 环境层正常但应用端口无监听/进程缺失 → 应用进程异常
   - 环境层正常且进程在线 → 应用自身（结合业务日志定位代码级）
6. **影响评估**：基于应用拓扑评估受影响业务与用户范围、是否有同集群备用节点。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：按分层快速定位不可用点并切换：LB/后端问题 → 切备；主机/VM宕 → 迁移；DB/中间件不可用 → 切副本/降级；应用进程未起 → 拉起/回滚。优先用备份路径恢复访问。
- 🔧 **根因处置（修复）**：修复定位到的具体层根因（网络/IaaS/PaaS/接入/应用），并做恢复验证。
- 🧭 **影响范围决策**：核心业务不可用 → 第一时间用冗余/降级恢复可用性，再定位并修根因；「不可用」优先于「根因」，先恢复。

## 6. 应用响应劣化（拨测时延升高/成功率下降）

**故障现象**：应用拨测成功率下降或响应时延显著超出基线，用户体验变慢但未完全不可用。

**根因类型**：
- 【网络】承载链路时延/丢包/抖动升高
- 【IaaS】承载主机CPU/内存饱和、磁盘IO瓶颈；存储IO慢传导
- 【PaaS】数据库慢查询/锁等待、中间件队列积压、连接池/线程池耗尽
- 【应用自身】GC停顿、内部锁竞争、低效代码

**分析步骤**：
1. **告警识别**：接收应用拨测时延/成功率偏离基线告警、响应时间告警。
2. **变更关联**：核查近期发布、流量变化、依赖组件变更。
3. **拓扑关联**：展开承载链各层节点与依赖组件。
4. **性能指标分析（时序对齐 + 找最早偏离层）**：对齐拨测时延曲线与各层关键指标（网络时延、主机CPU/IO、存储IO、数据库响应/慢查询、中间件积压、GC）的时序，定位最早劣化层。
5. **根因判定**：
   - 网络时延先升、应用时延随后 → 网络劣化（转 `rca-network.md`）
   - 主机资源/存储IO先恶化 → IaaS根因（转 `rca-iaas.md`）
   - 数据库慢查询/中间件积压先出现 → PaaS根因（转 `rca-paas.md`）
   - 各层指标均在基线内、仅应用内部耗时升高 → 应用自身（GC/锁/代码）
6. **影响评估**：评估劣化对业务响应与用户体验的影响程度。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：先按最早劣化层止血：网络 → 切换/保障QoS；主机/存储 → 迁移/扩容/限流；DB → 护缓存/切读/限流；应用自身 → 扩副本/限流降级、临时调GC。
- 🔧 **根因处置（修复）**：针对最早劣化层做根因修复（换链路/扩资源/优化SQL/优化代码GC）。
- 🧭 **影响范围决策**：关键业务体验劣化 → 先在最早劣化层扩容/限流/切换止血，再优化根因；轻微劣化可直接优化。

## 7. 应用部分功能/接口异常（部分拨测用例失败）

**故障现象**：多功能拨测中部分用例失败或变慢，其余正常——典型局部异常，常指向某个被依赖的局部组件或部分节点。

**根因类型**：
- 【PaaS局部】某个被特定功能依赖的下游服务/特定库/缓存异常
- 【网络局部】特定后端路径/特定ACL/特定网段问题
- 【IaaS局部】集群中部分节点异常（部分请求命中坏节点）
- 【应用自身】特定功能的业务逻辑/代码缺陷

**分析步骤**：
1. **告警识别**：识别哪些拨测用例失败、哪些正常，提取失败用例共性（同一接口/依赖/节点）。
2. **拓扑关联**：通过应用拓扑定位失败用例所依赖的特定组件/节点/网络路径（与正常用例做差集）。
3. **分层下钻**：仅针对失败用例涉及的那部分组件/节点/路径，检查其告警与指标。
4. **根因判定**：
   - 失败用例共享某异常的库/缓存/下游 → PaaS局部根因
   - 失败用例共享某条异常网络路径/ACL → 网络局部根因
   - 失败请求集中于集群某些节点且节点异常 → IaaS局部根因（坏节点）
   - 所涉组件/节点/路径全部正常 → 该功能的应用自身问题
5. **影响评估**：评估受影响的具体功能与用户范围，判断是否可临时摘除坏节点/降级。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：定位失败用例共性（坏节点/异常依赖/网络路径）→ 临时摘除坏节点、降级异常功能、切正常路径，保住整体可用。
- 🔧 **根因处置（修复）**：修复具体的局部依赖/坏节点/网络路径或功能代码缺陷。
- 🧭 **影响范围决策**：局部异常一般不必全局止血 → 摘除/降级异常局部先恢复大盘，再修局部根因。

## 8. 前端/用户侧故障

**故障现象**：用户侧体验异常——静态资源加载慢、网站无法访问、页面白屏或功能异常、特定机型异常，后端服务可能正常。

**根因类型**：
- CDN加速异常（静态资源加载慢、部分地区不可用、缓存命中率低）
- 域名解析故障（DNS解析失败、网站无法访问）
- 前端JS错误（页面功能异常、白屏）
- 移动端兼容性问题（特定机型/版本功能异常）

**分析步骤**：
1. **告警识别**：接收RUM用户侧告警（页面性能、错误率、地域分布）、多点拨测告警、CDN/DNS健康告警。
2. **变更关联**：核查近期前端发布、CDN配置、DNS记录、域名/证书变更。
3. **拓扑关联**：按地域/运营商/机型/客户端版本下钻，区分全局还是局部。
4. **性能指标分析**：查看CDN节点状态/命中率/回源、DNS解析成功率与时延、前端JS错误率与堆栈、页面性能（LCP/FID）、按机型/版本聚合的失败分布。
5. **根因判定**：
   - 部分地区资源慢 + CDN节点/命中率异常 → CDN异常
   - 解析失败 + DNS记录/可达异常 → 域名解析故障
   - 白屏/功能异常 + JS错误率激增（常伴前端发布）→ 前端代码问题
   - 失败集中于特定机型/版本 → 移动端兼容性问题
6. **影响评估**：评估受影响地域/用户群与功能范围，判断是否刷新缓存/切备用DNS/回滚前端/热修复。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：CDN/DNS异常 → 切备用CDN/DNS或回源、刷新缓存；前端JS致白屏 → 回滚前端版本；机型兼容 → 临时降级/提示。
- 🔧 **根因处置（修复）**：修复CDN配置/缓存、修DNS解析、修前端代码、做兼容适配。
- 🧭 **影响范围决策**：影响大面积用户访问 → 先切备用CDN/DNS或回滚前端止血，再修根因；小范围兼容问题可直接修。

## 9. 流量/并发类故障

**故障现象**：在高并发或突发流量下系统过载，响应时间飙升、服务过载或缓存/数据库被击穿，整体可用性下降。

**根因类型**：
- 突发流量冲击（QPS飙升、服务过载）
- 缓存击穿（热点key过期、数据库压力剧增）
- 缓存雪崩（大量缓存同时失效/缓存宕机）
- 数据库连接风暴（连接数瞬间打满）

**分析步骤**：
1. **告警识别**：接收QPS/响应时间/过载告警、缓存命中率骤降、数据库连接数告警。
2. **变更关联**：核查是否有营销活动/秒杀、缓存过期策略调整、限流配置变更。
3. **拓扑关联**：定位流量入口、缓存层、数据库及承载节点资源。
4. **性能指标分析**：查看实时QPS与基线偏离、缓存命中率与key过期分布、DB连接数/慢SQL、各层资源水位。
5. **根因判定**：
   - QPS大幅上偏 + 各层资源接近上限 → 突发流量冲击（弹性扩容/限流降级）
   - 命中率骤降集中于单热点key失效瞬间 → 缓存击穿
   - 大批key同时失效/缓存实例宕机 → 缓存雪崩
   - 连接数瞬间打满 + 慢SQL → 数据库连接风暴（转 `rca-paas.md` 数据库）
6. **影响评估**：评估过载对业务成功率与用户体验影响，判断扩容/限流/降级/多级缓存策略。

**⚑ 处置建议（先止血 · 后修复，按影响范围决策）**
- 🚑 **紧急预案（止血/降损）**：突发流量/连接风暴 → 立即限流、扩容、开启排队或降级非核心功能；缓存击穿/雪崩 → 加互斥/空值/随机过期、限流回源、临时扩缓存。
- 🔧 **根因处置（修复）**：扩容与容量规划、优化缓存策略（预热/多级/随机TTL）、连接池治理、压测调优。
- 🧭 **影响范围决策**：核心业务被流量冲击 → 先限流+扩容+护缓存止血，再做容量与缓存根因优化；可预期活动应提前预案。
