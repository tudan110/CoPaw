# 跨层复合故障根因分析（4场景）

> **能力边界说明**：跨层场景的"服务级传播追踪"理想上依赖APM调用链，而调用链当前**未接入**。
> 因此本章标注每条根因的当前支持程度：✅ 当前可支持（基于已接入的告警/指标/拓扑/变更可定位）；🔶 框架预留（需补充数据后才能自动定位）。

## 1. 级联故障

**故障现象**：单个组件故障导致多个上游服务异常，故障波及范围远超单点，形成雪崩效应。

**根因类型**：
- 雪崩效应（单点故障触发超时重试风暴，耗尽上游资源）🔶（资源/告警层面可观测，服务级重试传播追踪需APM）
- 故障扩散（共享依赖故障导致多条业务线受影响）✅（基于业务-资源映射可定位共享依赖）
- 依赖链断裂（核心服务不可用导致整条业务链中断）🔶（依赖关系定位✅，跨服务调用断裂确认需APM）
- 资源争抢（多个服务竞争同一资源导致全局性能下降）✅（同节点资源指标可定位）

**分析步骤**：
1. **告警识别**：接收多个服务同时报告异常的告警风暴，先做**时间/空间聚合去噪**，识别关联性。
2. **拓扑关联**：通过应用拓扑和网络拓扑追踪故障传播路径，确认故障源头和扩散范围（应用服务间调用级路径在APM接入后才完整）。
3. **变更关联**：核查源头组件是否有变更触发。
4. **性能指标分析**：查看各层服务的响应延迟、错误率、资源使用率等指标的时序变化，按时间先后定位"最早异常对象"。
5. **根因判定**：
   - 多个不相关业务同时受影响且共享同一依赖、该依赖最早异常 → 故障扩散 ✅
   - 多服务同节点资源同时升高 → 资源争抢 ✅
   - 单点故障后上游资源被打满/重试激增 → 雪崩效应 🔶（结合资源曲线推断，精确确认需APM）
6. **影响评估**：结合全层拓扑和业务指标，评估级联故障影响的业务范围和程度。

## 2. 网络-应用联合故障

**故障现象**：网络异常导致应用服务调用异常，或应用异常放大网络问题，表现为网络和应用同时异常。

**根因类型**：
- 网络抖动导致超时重试风暴（网络不稳定触发应用重试机制）✅（网络侧✅；应用重试量化需APM 🔶）
- DNS故障导致服务发现失败（DNS解析异常导致服务注册失败）🔶（DNS/服务注册数据未接入，仅能从"网络正常但服务大面积失败"间接推断）
- 网络分区故障导致脑裂（网络分区导致集群脑裂）🔶（网络分区✅；集群脑裂状态确认需集群/中间件侧数据）
- 网络延迟升高导致服务调用超时（网络问题被应用超时放大）✅（网络延迟✅；调用超时关联需业务-资源映射）

**分析步骤**：
1. **告警识别**：同时接收网络层告警（延迟升高、丢包、DNS异常）和应用层告警（服务调用失败、超时），确认两层告警的时间关联性。
2. **拓扑关联**：通过网络拓扑和应用拓扑的交叉关联，确认网络异常路径与应用异常服务的对应关系。
3. **性能指标分析**：对比网络延迟/丢包率与应用响应延迟/错误率的时序关系，确认因果时序（谁先谁后）。
4. **根因判定**：
   - 网络抖动在先且应用错误率随后上升 → 网络抖动传导 ✅（重试风暴需APM量化 🔶）
   - 网络延迟升高在先且应用超时在后 → 服务超时 ✅
   - 网络分区出现 + 集群多主/数据冲突征兆 → 脑裂 🔶
   - 网络正常但特定服务大面积解析/发现失败 → 疑似DNS/服务发现 🔶（需补数据确认）
5. **影响评估**：结合全层拓扑和业务指标，评估联合故障影响的业务范围和程度。

## 3. IaaS-PaaS联合故障

**故障现象**：IaaS层资源异常导致PaaS层服务异常，或PaaS层异常放大IaaS层问题，表现为基础设施和平台服务同时异常。

**根因类型**：
- 存储IO慢导致数据库性能劣化（存储层问题影响数据库性能）✅（基于已有存储指标与数据库指标）
- 主机资源耗尽导致中间件/数据库异常 ✅（基于IaaS指标+中间件指标）
- 宿主机故障导致Pod批量驱逐（宿主机Down导致上面所有Pod不可用）🔶（需虚拟化/容器数据）
- 网络IO异常导致服务网格不稳定（网络层问题影响服务网格）🔶（需服务网格数据）
- 资源超分导致容器调度异常（宿主机资源超分影响容器调度）🔶（需容器数据）

**分析步骤**：
1. **告警识别**：同时接收IaaS层告警（宿主机Down、存储IO异常、网络IO异常）和PaaS层告警（Pod驱逐、数据库慢查询、服务网格不稳定），确认两层告警的时间关联性。
2. **拓扑关联**：通过IaaS拓扑和应用拓扑的交叉关联，确认异常存储卷/主机挂载或承载的数据库/中间件实例。
3. **性能指标分析**：对比IaaS层资源指标（宿主机CPU/内存/磁盘IO/网络IO）与PaaS层服务指标（Pod状态、数据库响应、服务网格延迟）的时序关系。
4. **根因判定**：
   - 存储IO延迟升高在先、数据库慢查询增多在后 → 存储IO慢导致数据库性能劣化 ✅
   - 主机CPU/内存耗尽在先、中间件/数据库异常在后 → 主机资源耗尽传导 ✅
   - 宿主机Down且上面Pod全部不可用 → 宿主机故障导致Pod批量驱逐 🔶
5. **影响评估**：结合全层拓扑和业务指标，评估联合故障影响的业务范围和程度。

## 4. 全链路退化

**故障现象**：多个节点同时性能下降，但未达到告警阈值，业务整体变慢但未完全中断，用户体验明显下降。

**根因类型**：
- 多节点性能下降叠加（各层小问题累积导致全链路退化）
- 容量规划不足（流量增长超过各层容量规划）
- 流量突增叠加资源不足（突发流量叠加已有资源紧张）
- 全局性配置偏差（多层配置不优导致整体性能下降）

**分析步骤**：
1. **告警识别**：依赖**动态基线**捕捉"阈值下劣化"——接收多层性能指标轻度偏离基线告警或业务层用户体验指标异常告警。
2. **变更关联**：核查是否有全局性配置/参数变更。
3. **拓扑关联**：通过全层拓扑（网络+IaaS+PaaS+应用）检查各层节点的性能状态，确认退化的层次和位置。
4. **性能指标分析**：查看各层节点的性能指标时序变化，分析哪些节点退化最严重；检查流量模式是否有变化。
5. **根因判定**：
   - 各层小异常累积且单点均未超过严重阈值 → 多节点性能下降叠加
   - 流量持续增长且各层资源接近上限 → 容量规划不足
   - 突发流量叠加已有资源紧张 → 流量突增叠加资源不足
   - 命中全局配置变更 + 普遍性偏差 → 全局性配置偏差
6. **影响评估**：结合全层拓扑和业务指标，评估全链路退化影响的业务范围和程度。

## 分析方法论

### 六步分析法（统一流程）

| 步骤 | 名称 | 核心内容 |
|------|------|----------|
| 步骤1 | 告警识别 | 从syslog告警、阈值告警中识别故障事件，确认告警类型、对象、时间，形成故障初始线索 |
| 步骤2 | 变更关联 | 检查故障前24h内是否有配置变更、版本升级、割接、发布记录。变更命中是高优先级根因线索——大量故障由变更引入 |
| 步骤3 | 拓扑关联 | 通过网络拓扑、IaaS拓扑、应用拓扑确定故障对象位置，关联上下游依赖，确认影响范围 |
| 步骤4 | 性能指标分析 | 对相关指标做时序+动态基线（同环比）分析，识别突变、缓慢劣化与阈值下抖动 |
| 步骤5 | 根因判定 | 按判定规则匹配候选根因，给出置信度与排序（依据：证据条数、变更命中、时序先后、基线偏离幅度）。多候选时输出Top-N |
| 步骤6 | 影响评估 | 基于拓扑评估受影响业务/用户范围、冗余与备份状态，给出紧急程度 |

> **告警风暴处理**：当短时间出现大量关联告警时，先做时间/空间聚合去噪与根因收敛，避免将"故障表象"误判为多个独立根因。

> **动态基线**：阈值告警无法覆盖的劣化（如性能缓慢下降但未越过固定阈值），由动态基线偏离（同环比偏差超过N倍标准差）捕捉。

### 关键分析技术

| 技术方法 | 适用场景 | 数据依赖 |
|----------|----------|----------|
| 拓扑关联分析 | 故障定位、影响范围分析 | 网络拓扑、IaaS拓扑、应用拓扑 |
| 时序相关性分析 | 因果时序验证、故障传播路径分析 | 告警时间戳、性能指标时序数据 |
| 阈值异常检测 | 性能劣化、资源耗尽等场景 | 性能指标时序数据、阈值配置 |
| 告警风暴关联 | 级联故障、多服务同时异常 | 同时间窗内的多条告警 |
| 因果推理 | 复杂故障的根因定位 | 告警+指标+拓扑的融合数据 |
