# 专有大模型接口适配 OpenAI 协议 · 通用方案

## 1. 背景与目标

很多企业内部/行业大模型网关（如电信启明大模型）并不提供严格的 OpenAI 兼容接口：请求体字段看起来相似（`messages`/`temperature`/`stream` 等），但路径、鉴权方式、模型发现、流式返回结构往往与 OpenAI 标准不一致。

如果上层业务系统（agent 框架、IDE 插件、聊天应用等）只认标准 OpenAI 协议，直接把专有网关地址填进去是接不通的，会遇到：

- 路径不匹配（专有接口通常不是 `/v1/chat/completions`）
- 缺少标准 `Authorization: Bearer` 之外的额外鉴权字段（如自定义 APP-ID/APP-KEY、签名头）
- 没有标准的 `/v1/models` 模型发现接口
- 流式返回不是标准 SSE + `choices[].delta.content` 结构

本方案与具体技术栈无关，目标是给出一套**协议翻译层（Adapter）**的通用设计逻辑，任何语言/框架都可以照此实现。

## 2. 核心思路：加一层协议翻译网关

不要在业务系统内部为每个专有供应商写特判逻辑，而是在专有网关前面加一层轻量适配服务：

```
业务系统（只认标准 OpenAI 协议）
        │  标准请求
        ▼
   适配层 Adapter（协议翻译）
        │  专有协议请求
        ▼
   专有大模型网关（启明/其他）
```

对业务系统而言，适配层就是一个普通的 OpenAI-compatible provider：填 `base_url` + `api_key` + `model` 即可接入，换供应商只需要换一个适配层实现，业务代码零改动。

## 3. 适配层要做的四件事

### 3.1 鉴权翻译

专有接口的鉴权字段往往不止一个 Bearer Token，可能还需要额外的自定义 header（APP-ID、APP-KEY、签名等）。适配层负责：

- 从配置中读取这些凭证（不要硬编码在代码里）
- 按目标接口要求的格式拼装成对应的 header
- 如果目标接口要求签名算法，签名计算逻辑也封装在这一层，业务系统完全无感

**原则**：调用方如果自带 `Authorization`，优先透传调用方的值；调用方没带时，才回退到适配层自己配置的凭证。这样既支持"网关统一托管密钥"，也支持"调用方自带密钥"两种模式。

### 3.2 请求体翻译（归一化）

OpenAI 的消息体支持多模态（`content` 可以是文本+图片的数组结构），但很多专有接口只认纯文本字符串。适配层要做归一化：

- 能理解的字段原样保留
- 复杂结构（如多模态数组）降级为目标接口能理解的最简形式（如拼接成纯文本）
- 无法理解、无法降级的字段应明确丢弃或报错，不能原样透传导致上游直接报错

### 3.3 请求转发 + 响应翻译

把翻译好的请求发到专有网关的真实地址，再把响应包装回标准格式返回。需要分两条路径处理：

- **非流式**：等上游完整返回后，包一层标准状态码/格式原样转发
- **流式（SSE）**：不能等全部收完再转发，必须边收边转发（上游给一块就往调用方发一块），否则失去流式的意义；出错时也要能在流式过程中及时中断并返回明确错误

网络异常（连接失败、超时）要在适配层统一转换成标准 HTTP 错误状态码（如 502/504）返回给调用方，不能让底层异常裸抛出去，否则上层无法判断该重试还是该报错。

### 3.4 模型发现接口

即使目标接口没有标准的 `/models` 接口，适配层也应该自己提供一个「列出可用模型」的标准接口，返回适配层实际支持/配置的模型 ID 列表。这样业务系统可以：

- 在配置模型来源时做下拉选择/校验
- 做轻量的连通性/健康检查，不用真的发一次完整对话请求

**连接检查建议**：如果目标接口没有 `/models`，不要用 `/models` 做健康检查，改用一个最小化的对话请求（如 `max_tokens=1` 的 ping）来验证连通性。

## 4. 配置管理原则（与技术栈无关）

- **凭证不要硬编码**，统一放在可读写的配置来源（配置中心/数据库/密钥管理都行），支持运行时改配置立即生效，不需要重启/重新部署
- **配置解析要有优先级链**：显式配置 > 环境变量兜底 > 默认值，便于迁移期间新老配置共存，不用一刀切
- **敏感字段做掩码展示**，避免密钥在界面/日志里明文暴露
- **可参数化复用**：如果后续还要接第二个、第三个专有网关，字段大同小异（base_url / 认证字段 / 超时 / 模型列表），建议抽象出一套通用的"字段描述 + 存取"框架，新增一个供应商只需要声明字段列表，不用重写存取逻辑

## 5. 接入前建议先确认的四件事

1. 目标网关是否存在等价的模型列表/发现接口
2. 目标网关 `stream=true` 时的返回是否是标准 SSE
3. 目标网关非流式返回结构是否接近 OpenAI `chat.completion`（`choices[].message.content` 这类结构）
4. 目标网关的鉴权方式复杂度：是简单的 header/token，还是需要额外签名算法（签名类鉴权会显著增加适配层实现复杂度，需要单独设计验证）

其中第 2、3 点最关键，决定适配层要做"轻量转发"还是"深度格式转换"。

## 6. 不推荐的做法

不要在业务系统的通用 OpenAI 客户端逻辑里为某个专有供应商加特判（比如按 `base_url` 识别成某厂商就走特殊分支）。这类做法短期省事，但：

- 通用客户端逻辑会越改越臃肿
- 后续再接一个类似厂商就会继续堆特判
- 配置模型（前后端）始终不清晰，无法统一管理

专有协议的差异应该完全封装在独立的适配层里，业务系统只面对标准协议。

## 7. 落地检查清单

- [ ] 确认目标网关鉴权方式，实现鉴权翻译逻辑
- [ ] 实现请求体归一化（多模态 → 纯文本等降级处理）
- [ ] 实现非流式转发 + 错误状态码映射
- [ ] 实现流式（SSE）边收边转发
- [ ] 实现模型列表接口（`/models`），如无原生接口则手工维护
- [ ] 连接检查改用最小化对话请求，不依赖 `/models`
- [ ] 凭证配置支持运行时修改、敏感字段掩码展示
- [ ] 业务系统侧把适配层当成标准 OpenAI provider 接入（`base_url` + `api_key` + `model`）
