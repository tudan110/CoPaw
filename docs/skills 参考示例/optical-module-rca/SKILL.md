# Optical Module RCA（光模块老化根因分析）

为"核心路由器光模块疑似老化"这类故障，提供从参数到根因结论的最短
执行路径。这是一个**纯本地计算类 Skill**：不连接任何真实设备、不需要
任何账号或 Token，所有判断都基于用户/Agent 提供的具体数值，参考依据
完全来自 `references/` 目录下的文档。

## 前置配置（给 Agent）

**本技能不需要任何配置**。不需要 `.env`、不需要 Token、不需要网络
请求。执行前唯一要确认的是：用户是否已经提供了足够的参数（见下方
"必需参数"），如果没有，应先向用户询问，而不是编造数值去执行脚本。

## 触发条件（给 Agent）

当用户提到以下诉求时，优先使用本技能：

- 提供了光模块的具体参数（光功率、偏置电流、温度、CRC 错误等），
  询问是否异常、是否老化
- "这个端口是不是有问题" / "帮我定位一下根因" / "要不要换光模块"
- 已知某端口误码率上升、间歇性丢包，需要判断是否是光模块老化导致

若用户只是想看"当前有哪些告警"，这不是本技能的场景（那是查询类
诉求，不涉及根因分析）；若用户的问题和光模块/端口老化无关，不要使用
本技能。

## 必需参数

执行诊断前，必须先从用户那里拿到以下 5 项数值（脚本的必填参数）：

| 参数 | 含义 | 单位 |
|------|------|------|
| 端口名称 | 如 GE0/0/1 | - |
| 接收光功率 | rx_power | dBm |
| 发送光功率 | tx_power | dBm |
| 偏置电流 | bias_current | mA |
| 温度 | temperature | °C |
| CRC 错误计数增长速率 | crc_rate | 个/秒 |

如果用户没有一次性给全，应该明确追问缺哪几项，不要用假数据替代
执行，也不要跳过某一项直接下结论。

以下 2 项是可选参数，没有也能出结论，但提供了可以让判断更准确：

| 参数 | 含义 | 单位 |
|------|------|------|
| 下游告警延迟 | 下游设备告警比该端口告警晚多少分钟 | 分钟 |
| 对端接收光功率 | 对端设备的接收光功率 | dBm |

## 最短路径（给 Agent）

```bash
python3 scripts/diagnose_optical_aging.py \
    --port <端口名称> \
    --rx-power <接收光功率> \
    --tx-power <发送光功率> \
    --bias-current <偏置电流> \
    --temperature <温度> \
    --crc-rate <CRC错误速率> \
    [--downlink-alert-delay-min <分钟数>] \
    [--peer-rx-power <对端接收光功率>] \
    [--affected-users <受影响用户数>] \
    --output markdown
```

- 聊天窗口场景优先使用 `--output markdown`（默认值）
- 需要结构化数据时使用 `--output json`
- 脚本退出码：`0` 表示各项参数均正常，`1` 表示存在异常，可用于快速
  判断"要不要继续往下分析"，不需要额外解析输出内容

## 主流程（给 Agent）

### 1. 检查参数是否齐全

必需参数缺失时，直接列出缺哪几项并请用户补充，不要执行脚本。

### 2. 执行诊断脚本

按上方"最短路径"命令执行，把用户提供的数值原样传入对应参数。

### 3. 解读脚本输出

脚本已经完成了"指标验证 + 拓扑校验 + 根因判定 + 处置建议"，Agent
不需要重新计算，只需要把脚本输出组织成对用户友好的回复：

- 先给结论（根因是什么、置信度多少）
- 再给关键异常指标（不需要罗列全部 5 项，异常的重点说）
- 最后给处置建议，按"紧急止血 / 根因修复 / 预防措施"分层说明

### 4. 如果用户要"正式故障报告"

参考 `references/report-template.md`，补充脚本无法自动生成的字段
（故障编号、发生时间、修复时间），不要把脚本原始输出直接当作故障
报告发出去。

## 用户意图 -> 推荐动作

- "帮我看看这个端口是不是光模块老化" → 收集 5 项必需参数后执行诊断脚本
- "这个光模块要不要换" → 执行诊断脚本，读处置建议里的"根因修复"部分回答
- "先别换模块，会不会是光纤的问题" → 补充询问对端接收光功率，传
  `--peer-rx-power` 参数，看拓扑校验部分的结论
- "帮我写一份故障报告" → 先执行诊断脚本，再参考
  `references/report-template.md` 补全人工字段

## 输出约定

- 默认输出适合聊天窗口直接展示的 Markdown（脚本已经生成好表格和分段，
  Agent 一般不需要再重新排版）
- 先给 1~2 句结论（根因 + 置信度 + 严重程度），再给指标明细表格，
  最后给处置建议
- 如果异常指标较多，也要全部列出（这个场景数据量小，不需要像告警
  列表那样做"只展示前 20 条"的截断）
- 不要把 JSON 原始输出直接发给用户，除非用户明确要求原始数据

## 错误处理规则

- **必需参数缺失**：直接列出缺失的参数名，不要猜测或使用默认值
- **数值明显不合理**（如温度 -50°C、光功率 100dBm）：提示用户确认
  数据来源是否正确，不要直接当正常数据处理
- **只有部分可选参数**：正常执行，脚本会在拓扑校验部分注明"跳过"
  哪一项，Agent 转述时如实说明即可

## 何时读取参考文档

- 用户问"这套方法是怎么来的""为什么这么判断"时，读取
  `references/methodology.md`（四步法完整说明）
- 用户问某个参数的具体正常范围、故障值示例时，读取
  `references/threshold-reference.md`
- 用户问处置动作的具体做法、风险、优先级时，读取
  `references/remediation-playbook.md`
- 用户要生成正式故障报告时，读取 `references/report-template.md`

默认不主动加载全部参考文档；只在需要解释细节时再读。

## Few-shot 示例

### 示例 1：完整参数诊断

- 用户：GE0/0/1 这个口，接收光功率 -23.5dBm，发送光功率 -3.2dBm，
  偏置电流 68mA，温度 78 度，CRC 错误速率大概 100/s，帮我看看是不是
  光模块老化
- 动作：执行
  `python3 scripts/diagnose_optical_aging.py --port GE0/0/1 --rx-power -23.5 --tx-power -3.2 --bias-current 68 --temperature 78 --crc-rate 100 --output markdown`
- 回复：先说明"判断为光模块老化，置信度约 88%，严重程度：严重"，
  再列出接收光功率/偏置电流/温度/CRC 四项异常指标，最后给出"切换
  备用链路 → 更换光模块"的处置建议

### 示例 2：参数不全

- 用户：这个端口好像有点问题，能帮我看看吗
- 回复：不要执行脚本，直接说明需要用户提供哪 5 项参数（端口名称、
  接收光功率、发送光功率、偏置电流、温度、CRC 错误速率），并给出
  简短示例格式

### 示例 3：怀疑是光纤问题

- 用户：会不会是光纤的问题，不是光模块本身？
- 动作：询问用户是否知道对端设备的接收光功率，如果有，补充
  `--peer-rx-power` 参数重新执行诊断脚本
- 回复：根据拓扑校验结果说明——如果对端也异常，明确提示"更可能是
  光纤衰减，建议先排查光纤和对端，而不是直接换本端光模块"

### 示例 4：生成故障报告

- 用户：帮我整理一份故障报告，故障编号 FT20260708001，今天上午
  9:15 发现的
- 动作：先执行诊断脚本拿到根因结论和处置建议，再参考
  `references/report-template.md` 的字段顺序，把用户提供的故障编号、
  发生时间和脚本输出的根因、处置动作拼成完整报告
- 回复：按模板格式输出完整故障报告，"修复时间"留空提示用户后续补充

## 注意事项

- 本技能所有判断依据均来自内部固定的经验阈值表（见
  `references/threshold-reference.md`），不代表所有厂商、所有型号
  光模块的通用标准，实际生产环境使用前应结合自己的设备手册核实
- 置信度算法是简化实现，用于演示"综合判断"这个思路，不是严格的
  概率模型
- 脚本不做任何网络请求、不读取任何配置文件，可以放心在任何环境下
  直接运行
