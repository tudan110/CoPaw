# Optical Module RCA（光模块老化根因分析）

为"核心路由器光模块疑似老化"这类故障，提供从端口名称到根因结论的
最短执行路径。这是一个**纯本地计算类 Skill**：不连接任何真实设备、
不需要任何账号或 Token，也不需要用户提供光功率、电流、温度等具体
数值（这是一份演示 demo，参数由脚本内置的模拟数据自动生成），判断
依据的参考资料完全来自 `references/` 目录下的文档。

## 前置配置（给 Agent）

**本技能不需要任何配置**。不需要 `.env`、不需要 Token、不需要网络
请求。**也不需要用户提供光功率、电流、温度等具体数值** —— 这是一份
演示 demo，诊断脚本自带 `scripts/mock_data.json`（几个典型案例：老化
案例 `GE0/0/1`、正常案例 `GE0/0/2`、疑似光纤问题案例 `GE0/0/3`），
只要给出端口名称，脚本就会自动取数并给出完整结论。执行前唯一要确认
的是：用户有没有提到想看哪个端口（没提到就默认按 `GE0/0/1` 演示，
或直接询问用户想看哪个端口）。

## 触发条件（给 Agent）

当用户提到以下诉求时，优先使用本技能：

- 提供了光模块的具体参数（光功率、偏置电流、温度、CRC 错误等），
  询问是否异常、是否老化
- "这个端口是不是有问题" / "帮我定位一下根因" / "要不要换光模块"
- 已知某端口误码率上升、间歇性丢包，需要判断是否是光模块老化导致

若用户只是想看"当前有哪些告警"，这不是本技能的场景（那是查询类
诉求，不涉及根因分析）；若用户的问题和光模块/端口老化无关，不要使用
本技能。

## 参数来源

**用户只需要说明端口名称**（如 GE0/0/1），不需要提供光功率、电流、
温度等具体数值——脚本会自动从内置的 `scripts/mock_data.json` 里按
端口名称取一整套模拟采集数据（真实生产环境里这些数据应该来自监控
系统，demo 场景用 mock 数据代替，方便演示完整流程）：

| 端口 | 案例类型 |
|------|----------|
| GE0/0/1 | 典型老化案例（多项指标异常，置信度高） |
| GE0/0/2 | 正常案例（各项指标均正常） |
| GE0/0/3 | 疑似光纤问题案例（本端和对端都异常） |

用户提到其他端口名称、或者没有提到任何端口时，脚本会退回 GE0/0/1
这个默认案例，同样能给出完整结论——不用因为"端口不在列表里"就拒绝
执行或反问用户要参数。

（脚本保留了 `--rx-power` 等参数用于开发调试时临时覆盖某一项数值，
但正常对话场景下不需要用到，也不需要向用户询问这些数值。）

## 最短路径（给 Agent）

```bash
python3 scripts/diagnose_optical_aging.py --port <端口名称> --output markdown
```

- 聊天窗口场景优先使用 `--output markdown`（默认值）
- 需要结构化数据时使用 `--output json`
- 脚本退出码：`0` 表示各项参数均正常，`1` 表示存在异常，可用于快速
  判断"要不要继续往下分析"，不需要额外解析输出内容

## 主流程（给 Agent）

### 1. 确认端口名称

用户提到了具体端口名称就直接用；没提到就默认用 GE0/0/1 演示，或
直接询问用户想看哪个端口，不需要额外询问光功率、电流等数值。

### 2. 执行诊断脚本

按上方"最短路径"命令执行，只传 `--port`，参数由脚本自动从 mock 数据
取值。

### 3. 解读脚本输出

脚本已经完成了"指标验证 + 拓扑校验 + 根因判定 + 处置建议"，Agent
不需要重新计算，只需要把脚本输出组织成对用户友好的回复：

- 先给结论（根因是什么、置信度多少）
- 再给关键异常指标（不需要罗列全部 5 项，异常的重点说）
- 最后给处置建议，按"紧急止血 / 根因修复 / 预防措施"分层说明

### 4. 如果用户要"正式故障报告"

参考 `references/report-template.md`，补充脚本无法自动生成的字段
（故障编号、发生时间、修复时间），不要把脚本原始输出直接当作故障
报告发出去。

## 用户意图 -> 推荐动作

- "帮我看看这个端口是不是光模块老化" → 确认端口名称后直接执行诊断脚本
- "这个光模块要不要换" → 执行诊断脚本，读处置建议里的"根因修复"部分回答
- "先别换模块，会不会是光纤的问题" → 执行诊断脚本，看拓扑校验部分
  对"对端接收光功率"的结论（示例数据里 GE0/0/3 就是这类案例）
- "帮我写一份故障报告" → 先执行诊断脚本，再参考
  `references/report-template.md` 补全人工字段

## 输出约定

- 默认输出适合聊天窗口直接展示的 Markdown（脚本已经生成好表格和分段，
  Agent 一般不需要再重新排版）
- 先给 1~2 句结论（根因 + 置信度 + 严重程度），再给指标明细表格，
  最后给处置建议
- 如果异常指标较多，也要全部列出（这个场景数据量小，不需要像告警
  列表那样做"只展示前 20 条"的截断）
- 不要把 JSON 原始输出直接发给用户，除非用户明确要求原始数据

## 错误处理规则

- **用户没提端口名称**：默认用 GE0/0/1 演示，或直接询问用户想看
  哪个端口，不要因为缺端口名称就拒绝执行
- **用户明确要求用某个具体数值覆盖 mock 数据**（如"假设温度是 90 度
  会怎样"）：把该数值通过对应的 `--temperature` 等参数传给脚本，
  其余参数仍取自 mock 数据

## 何时读取参考文档

- 用户问"这套方法是怎么来的""为什么这么判断"时，读取
  `references/methodology.md`（四步法完整说明）
- 用户问某个参数的具体正常范围、故障值示例时，读取
  `references/threshold-reference.md`
- 用户问处置动作的具体做法、风险、优先级时，读取
  `references/remediation-playbook.md`
- 用户要生成正式故障报告时，读取 `references/report-template.md`

默认不主动加载全部参考文档；只在需要解释细节时再读。

## Few-shot 示例

### 示例 1：完整参数诊断

- 用户：GE0/0/1 这个口，帮我看看是不是光模块老化
- 动作：执行 `python3 scripts/diagnose_optical_aging.py --port GE0/0/1 --output markdown`
- 回复：先说明"判断为光模块老化，置信度约 88%，严重程度：严重"，
  再列出接收光功率/偏置电流/温度/CRC 四项异常指标，最后给出"切换
  备用链路 → 更换光模块"的处置建议

### 示例 2：没提到具体端口

- 用户：这个端口好像有点问题，能帮我看看吗
- 动作：直接执行 `python3 scripts/diagnose_optical_aging.py --port GE0/0/1 --output markdown`（默认演示案例），或先反问用户是哪个端口
- 回复：给出诊断结论，同时说明这是按默认端口 GE0/0/1 演示的结果，
  如果用户指的是别的端口，请补充端口名称重新诊断

### 示例 3：怀疑是光纤问题

- 用户：GE0/0/3 这个口，会不会是光纤的问题，不是光模块本身？
- 动作：执行 `python3 scripts/diagnose_optical_aging.py --port GE0/0/3 --output markdown`
- 回复：根据拓扑校验结果说明——GE0/0/3 这个案例里对端接收光功率也
  异常，明确提示"更可能是光纤衰减，建议先排查光纤和对端，而不是
  直接换本端光模块"

### 示例 4：生成故障报告

- 用户：帮我整理一份故障报告，故障编号 FT20260708001，今天上午
  9:15 发现的
- 动作：先执行诊断脚本拿到根因结论和处置建议，再参考
  `references/report-template.md` 的字段顺序，把用户提供的故障编号、
  发生时间和脚本输出的根因、处置动作拼成完整报告
- 回复：按模板格式输出完整故障报告，"修复时间"留空提示用户后续补充

## 注意事项

- 本技能所有判断依据均来自内部固定的经验阈值表（见
  `references/threshold-reference.md`），不代表所有厂商、所有型号
  光模块的通用标准，实际生产环境使用前应结合自己的设备手册核实
- 置信度算法是简化实现，用于演示"综合判断"这个思路，不是严格的
  概率模型
- 脚本不做任何网络请求、不读取任何配置文件，可以放心在任何环境下
  直接运行
- **参数目前全部来自 `scripts/mock_data.json`，是演示数据，不是任何
  真实设备的实时采集值**。省队伍照这个 demo 改造自己的场景时，如果
  需要接真实数据源，只需要把 `resolve_metrics()` 里"从 mock 数据取值"
  这部分替换成调用自己的监控接口，其余判断逻辑不用改
