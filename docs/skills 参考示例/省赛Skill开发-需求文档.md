# 省赛 Skill 开发 —— 需求文档

> 背景：省里要组织 Skill 编写比赛，领导要求（1）给省里提供一份 Skill demo 作为模板参考；（2）同时让省里的参赛队伍提交对应的"场景文档"，说明自己 Skill 要解决什么场景。本文档给出这两部分的落地方案。

## 一、Demo 推荐

### 1.1 推荐方案：`docs/skills 参考示例/real-alarm`

推荐把 [real-alarm](real-alarm) 作为提供给省里的 Skill 编写参考 demo（本次已同步更新，见下方"本次更新内容"）。

### 1.2 推荐理由

- **场景典型，足够简单**：一个"查询 + 统计分析"型 Skill，是最常见、最容易上手的 Skill 类型，省队伍参照它写自己的场景不会被复杂的业务耦合带偏。
- **结构完整，覆盖 Skill 开发的核心规范**：包含 `SKILL.md`（frontmatter、触发条件、主流程、用户意图映射、输出约定、错误处理、Few-shot 示例）+ `scripts/`（分层：`get_*.py` 原始查询 / `analyze_*.py` 统一分析入口 / `query_*_count.py` 独立统计 / `utils/` 内部模块）+ `references/`（按需加载的参考文档），是"什么是一个规范的 Skill"最完整的样板。
- **不依赖我们内部系统**：本次已经改造为**通用 Skill**——配置走 `.env` 文件（而不是我们内部的设置页/DB），不依赖 `ProviderManager`、内部环境变量命名等特殊化代码，接到别的 Agent 框架里也能直接用。省队伍环境里没有我们的内部平台，这一点是能不能真正拿去用的前提。
- **无接口权限也能跑通**：新增了 `USE_MOCK_DATA=true` + `mock_data.json`，省队伍在没有拿到真实接口权限前，可以先用 mock 数据跑通参数解析、过滤、渲染逻辑，不会被"要不到接口账号"卡住整个学习节奏。
- **执行环境自包含**：保留 `uv run` + `pyproject.toml` 的方式（没有跟随我们内部"烘焙 requirements.txt + python3 直跑"的优化），省队伍拿到 demo 目录就能独立运行，不依赖我们内部的镜像构建链路。

### 1.3 本次更新内容（相对旧版 demo）

旧版 demo 的接口示例还停留在我们已经废弃的旧告警接口（`POST /resource/realalarm/list`）。本次同步了生产环境此前已完成的告警查询接口迁移，具体改动：

- 查询接口切换为 `GET /resource/alarm/statistics/hisAlarmList`，请求参数从 body 改为 query string。
- 新接口**强制要求** `beginTime`/`endTime` 时间窗，demo 增加了 `REAL_ALARM_QUERY_WINDOW_HOURS`（默认 24 小时）自动回溯生成时间窗的兜底逻辑。
- 状态字段语义反转：旧接口 `alarmstatus=1` 表示活跃，新接口改用 `isClear`（`0` 表示活跃）；demo 内部做了转换，Agent 侧接口不变（仍然传 `--alarm_status`）。
- 资源分类过滤字段从 `neAlias` 改为 `alarmClassType`；精确 IP 过滤改用 `neIp`；不再支持按 CI ID 精确过滤，回退为模糊搜索 `queryKey`。
- 同步清理了旧接口遗留但从未生效的死参数（如按城市过滤 `cities`——新旧接口都不支持，这次在文档里明确标注为"接受但不生效"，而不是像生产代码里那样悄悄失效）。
- `.env.example`、`mock_data.json`、`README.md` 目录结构说明、`SKILL.md`、`references/*.md` 全部同步更新。

## 二、场景文档要求（给省里参赛队伍）

参赛队伍在开发自己的 Skill 前，需要先提交一份"场景文档"，说明清楚要解决什么问题、怎么落地、怎么验证。目的是让评审和指导老师能在真正开始写代码之前，判断这个场景是否清楚、是否可落地，避免队伍一上来就直接写脚本、场景想到哪写到哪。

### 2.1 场景文档结构（建议模板）

| 章节 | 要求参赛队伍回答的问题 |
|------|----------------------|
| 1. 业务背景 | 这个 Skill 服务于什么业务/角色？现在这个问题是怎么解决的（人工 / 没有解决）？为什么值得用 Skill 来做？ |
| 2. 用户意图与触发场景 | 用户会用什么样的自然语言提问触发这个 Skill？列出至少 5 条真实问法示例。哪些问法**不应该**触发它（避免误判）？ |
| 3. 数据源与接口 | 数据从哪来？是现成的 API、数据库，还是需要新接的第三方系统？接口的鉴权方式、请求/响应示例是什么？如果暂时拿不到真实接口权限，打算怎么先跑通（mock 数据）？ |
| 4. 核心执行流程 | 从用户提问到给出答案，中间要几步？哪些是可以让 Agent 直接执行的确定性步骤（避免让大模型自由发挥、反复试错）？ |
| 5. 期望输出 | 期望 Skill 给用户返回什么形式的结果（一句话结论、表格、图表）？聊天场景下的输出格式要求是什么？ |
| 6. 异常与边界场景 | 数据为空、接口报错、参数缺失、结果过多等情况，期望 Skill 分别怎么处理？ |
| 7. 验收方式 | 怎么证明这个 Skill 做对了？给出至少 3 个"输入问题 → 期望结果"的验收用例。 |

### 2.2 提交要求

- 场景文档需要在**开始写 Skill 代码之前**提交，用于评审组判断场景是否清晰可落地。
- 字数不做硬性要求，但第 2、3、7 节（触发问法、数据源、验收用例）必须给出具体例子，不能只写抽象描述。
- 可以直接参考 `real-alarm` demo 的 `references/usage-scenarios.md`（问法 → 推荐动作的映射方式）和 `SKILL.md` 里的"Few-shot 示例"章节作为写法参照。

## 三、待确认事项

- 上述 demo 和场景文档模板尚未与省里正式沟通，需要确认省队伍的实际技术栈/运行环境是否与 `uv run` + Python 一致，若不一致可能需要额外补一份"非 Python 环境改造指引"。
- 场景文档模板中的"验收方式"章节目前只是建议，具体评分标准（是否计入比赛评分、占比多少）需要与领导/赛事组进一步确认。
