# AI 辅助轻应用开发方案

## 一、需求背景

在 IT 运维和业务交付场景中，客户经常需要定制化的展示页面：

- 报表呈现（设备统计、告警趋势、容量分析等）
- 固定查询（按条件查 CMDB、查指标、查告警历史）
- 任务固化（巡检报告页、故障复盘页、运营看板）

但客户通常不具备前端开发能力，无法自行编写 HTML/JS/CSS。

**核心诉求**：用户通过自然语言对话描述需求，AI 充当程序员角色，生成可运行的 HTML 应用页面，发布后可在"应用市场"中快速访问使用。

## 二、与现有功能的关系

| 功能 | 定位 | 区别 |
|------|------|------|
| 轻应用工坊（现有） | 对话问答的归档与复用 | 保存的是"对话流程"，不是独立页面 |
| **AI 辅助应用开发（本需求）** | 用户描述 → AI 写代码 → 发布独立应用 | 产出物是可独立运行的 HTML 页面 |
| HTML 成果发布服务（已有方案） | 底层发布能力 | 本需求的发布环节依赖该服务 |

## 三、核心能力定义

### 3.1 对话式开发

用户用自然语言描述需求，AI 生成完整可运行的 HTML 页面。

**交互示例**：

```
用户：帮我做一个按地市统计网络设备数量的柱状图，用 ECharts
AI：[生成 HTML 页面，包含 ECharts 柱状图，JS 调用 CMDB 接口查询数据]
用户：颜色改成蓝色渐变，再加一个饼图显示厂商占比
AI：[修改 HTML，新增饼图]
用户：可以了，发布
AI：[调用发布服务，返回访问链接]
```

### 3.2 实时预览

- 每次 AI 生成或修改 HTML 后，用户可以立即预览效果
- 预览环境与最终发布环境行为一致
- 不满意可以继续用自然语言迭代修改

### 3.3 数据对接

生成的 HTML 页面中的 JS 可以调用后端 API 查询真实数据：

- CMDB 资源查询（设备、拓扑、模型）
- 指标数据查询（性能、容量、趋势）
- 告警数据查询（当前告警、历史告警、统计）
- 工单数据查询（状态、进度、统计）
- 其他已有业务 API

### 3.4 发布上线

用户确认满意后，一键发布：

- 生成稳定的访问 URL
- 在应用市场中可见
- 支持分享给其他用户

### 3.5 应用管理

已发布的应用支持全生命周期管理：

- 查看 / 打开
- 修改（重新进入对话，迭代开发）
- 版本管理（保留历史版本）
- 下线 / 删除
- 分享 / 权限控制

## 四、AI 应用开发工作台

### 4.1 工作台布局

开发工作台采用**左右分栏**设计，左侧对话驱动开发，右侧实时预览效果：

```
┌────────────────────────────────────────────────────┐
│              AI 应用开发工作台                        │
│                                                    │
│  ┌──────────────────┐  ┌────────────────────────┐  │
│  │    对话区域        │  │      实时预览区域       │  │
│  │                  │  │                        │  │
│  │  用户：做个告警    │  │  ┌──────────────────┐  │  │
│  │  TOP10 柱状图     │  │  │                  │  │  │
│  │                  │  │  │   iframe 预览     │  │  │
│  │  AI：好的，已生成  │  │  │   (实时渲染)      │  │  │
│  │  [预览已更新 →]   │  │  │                  │  │  │
│  │                  │  │  └──────────────────┘  │  │
│  │  用户：颜色改蓝色  │  │                        │  │
│  │                  │  │  [发布] [全屏] [代码]   │  │
│  │  AI：已修改       │  │                        │  │
│  │  [预览已更新 →]   │  │                        │  │
│  └──────────────────┘  └────────────────────────┘  │
└────────────────────────────────────────────────────┘
```

### 4.2 交互流程

1. 用户从"成果应用"面板点击"新建应用"进入开发工作台
2. 左侧对话区：用户用自然语言描述需求
3. AI 生成 HTML 代码后，右侧 iframe 自动渲染预览
4. 用户在对话中提出修改意见（"改颜色""加个表格""数据换成折线图"）
5. AI 修改 HTML，右侧预览自动刷新
6. 反复迭代直到满意
7. 点击"发布"按钮，调用 Tool 将 HTML 发布到成果应用

### 4.3 工作台功能

**对话区域**：
- 与 AI 对话，描述需求和修改意见
- 对话上下文保持，AI 记住之前生成的完整代码
- 每次 AI 回复中如果包含 HTML 代码，自动推送到预览区

**预览区域**：
- iframe 沙箱渲染 HTML
- 实时更新，无需手动刷新
- 工具栏：发布 / 全屏预览 / 查看源码 / 切换设备尺寸（PC/平板/手机）

### 4.4 发布方式：Tool 而非 Skill

发布采用**原生 Tool（函数调用）**而非 Skill（shell 脚本）：

| 维度 | Tool（推荐） | Skill |
|------|------------|-------|
| 性能 | 直接函数调用，零开销 | 启动 Python 进程 + shell |
| 可靠性 | 不经过 shell 审批 | 可能被 shell 审批拦截 |
| 数据传递 | 直接传参，无大小限制 | HTML 内容通过 shell 参数传递困难 |
| 结果返回 | 直接返回 URL | 需要解析 stdout |

Tool 签名：
```
publish_html_artifact(
    title: str,        # 应用标题
    html_content: str, # HTML 完整内容
    description: str,  # 应用描述
    type: str,         # app | widget | dashboard
    tags: list[str],   # 标签
) → { id, url, title }
```

### 4.5 入口位置

- 从"成果应用"面板顶部的"新建应用"按钮进入
- 也可从对话中触发（用户说"帮我开发一个应用"时，AI 建议进入开发工作台）

### 架构说明

**发布的 HTML 放在前端 nginx 服务中**，而不是独立发布服务或后端服务：

| 决策 | 原因 |
|------|------|
| HTML 由前端 nginx serve | HTML 本质是前端静态资源，nginx 做这件事最合适 |
| 同域部署 | 发布的页面与后端 API 同域（都在 Portal 域下），天然无跨域问题 |
| 共享存储衔接 | 后端生成 HTML 写入共享存储，nginx 直接 serve 该目录 |
| 不增加服务 | 不需要新增独立发布服务，只需 nginx 加一个 location 配置 |

**nginx 配置示例**：

```nginx
server {
    # Portal SPA
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }

    # 用户发布的 HTML 应用（静态文件直出）
    location /artifacts/ {
        alias /data/artifacts/;
        index index.html;
        try_files $uri $uri/ =404;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://backend:8000/api/;
    }
}
```

**发布链路**：

1. 用户在对话中确认发布
2. 后端将 HTML 写入共享存储 `/data/artifacts/{app-id}/index.html`
3. 后端注册应用元数据（标题、作者、创建时间、类型等）
4. 返回访问 URL：`https://portal.example.com/artifacts/{app-id}/`
5. 前端 nginx 直接 serve 该文件，无需额外处理

## 六、数据存储设计

### 5.1 存储目录结构

所有数据统一存放在工作目录 `~/.qwenpaw/extensions/app-artifacts/` 下：

```
~/.qwenpaw/extensions/app-artifacts/
├── artifacts.db              ← SQLite 数据库（结构化元数据）
├── html/                     ← HTML 文件存储（nginx serve 的目标目录）
│   ├── {app-id}/
│   │   └── index.html
│   ├── {app-id-2}/
│   │   └── index.html
│   └── ...
└── thumbnails/               ← 应用缩略图（可选，后期）
```

### 5.2 存储职责划分

| 数据 | 存储方式 | 说明 |
|------|---------|------|
| 应用元数据 | SQLite `artifacts.db` | 标题、作者、创建时间、状态、类型、描述 |
| 应用版本记录 | SQLite `artifacts.db` | 版本号、发布时间、关联 HTML 路径 |
| 卡片配置 | SQLite `artifacts.db` | 参数 schema（JSON）、支持的尺寸规格 |
| 仪表盘布局 | SQLite `artifacts.db` | 包含哪些卡片、布局 JSON、各卡片参数 |
| 开发会话关联 | SQLite `artifacts.db` | 应用 ID ↔ 会话 ID 映射，支持迭代修改 |
| HTML 文件 | 文件系统 `html/` | 实际页面文件，nginx 直接 serve |
| 缩略图 | 文件系统 `thumbnails/` | 应用市场列表展示用（后期） |

### 5.3 SQLite 表结构设计（初版）

```sql
-- 应用/卡片主表
CREATE TABLE apps (
    id TEXT PRIMARY KEY,              -- UUID 或短 ID
    title TEXT NOT NULL,              -- 应用标题
    description TEXT,                 -- 应用描述
    type TEXT NOT NULL DEFAULT 'app', -- app | widget | dashboard
    status TEXT NOT NULL DEFAULT 'published', -- draft | published | offline
    author TEXT,                      -- 创建者
    session_id TEXT,                  -- 关联的开发会话 ID（用于迭代）
    html_path TEXT,                   -- HTML 文件相对路径
    config JSON,                      -- 配置信息（卡片参数 schema、尺寸等）
    tags TEXT,                        -- 标签（逗号分隔）
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 版本记录
CREATE TABLE app_versions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    app_id TEXT NOT NULL REFERENCES apps(id),
    version INTEGER NOT NULL,         -- 版本号（递增）
    html_path TEXT NOT NULL,          -- 该版本的 HTML 文件路径
    changelog TEXT,                   -- 变更说明
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 仪表盘布局（仪表盘由多个卡片组成）
CREATE TABLE dashboard_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    dashboard_id TEXT NOT NULL REFERENCES apps(id),  -- 仪表盘 app ID
    widget_id TEXT NOT NULL REFERENCES apps(id),     -- 卡片 app ID
    position_x INTEGER NOT NULL DEFAULT 0,           -- 网格列位置
    position_y INTEGER NOT NULL DEFAULT 0,           -- 网格行位置
    width INTEGER NOT NULL DEFAULT 1,                -- 占几列
    height INTEGER NOT NULL DEFAULT 1,               -- 占几行
    config JSON                                      -- 该卡片在此仪表盘中的参数配置
);

-- 索引
CREATE INDEX idx_apps_type ON apps(type);
CREATE INDEX idx_apps_status ON apps(status);
CREATE INDEX idx_app_versions_app_id ON app_versions(app_id);
CREATE INDEX idx_dashboard_items_dashboard_id ON dashboard_items(dashboard_id);
```

### 5.4 设计说明

**为什么用 SQLite**：
- 应用元数据需要查询、过滤、分页，关系型数据库最合适
- SQLite 零部署成本，单文件嵌入后端服务即可
- QwenPaw 项目中已有 SQLite 使用惯例
- 数据量级（几百~几千个应用）完全在 SQLite 承载范围内

**为什么 HTML 文件单独存储**：
- nginx 需要直接 serve 文件目录，不能从数据库读
- 文件可能较大（含内嵌图表库、CSS 等）
- 文件系统层面方便做备份和清理

**nginx 指向关系**：
- nginx 的 `/artifacts/` location alias 指向 `~/.qwenpaw/extensions/app-artifacts/html/`
- Helm 部署时通过 PVC 挂载该目录到前端 Pod

## 七、关键技术问题

### 5.1 页面内 JS 调接口的鉴权与代理

发布的 HTML 页面与 Portal 同域部署，调用后端 API 直接走 `/api/` 路径，**无跨域问题**。

鉴权方案：

| 方案 | 说明 | 适用场景 |
|------|------|---------|
| Cookie 透传 | 用户已登录 Portal，cookie 自动携带 | 需要用户登录后才能访问的应用 |
| 内嵌 Token | 发布时将受限 token 写入 HTML | 公开分享、无需登录的应用 |
| API Key | 应用级别的 API Key，限定可访问的接口范围 | 需要接口白名单控制 |

**推荐**：优先使用 Cookie 透传（最简单），对于需要公开分享的应用再引入内嵌 Token。

### 5.2 数据刷新策略

| 策略 | 适用场景 | 说明 |
|------|---------|------|
| 实时查询 | 固定查询类应用 | 每次打开页面时 JS 调接口查最新数据 |
| 定时刷新 | 看板类应用 | 页面内 setInterval 定时轮询 |
| 静态快照 | 报告类应用 | 发布时数据已内嵌，不再更新 |

AI 在生成页面时根据用户需求场景自动选择合适策略。

### 5.3 应用迭代

用户说"把图表颜色改一下"时，需要能在原应用基础上修改并重新发布：

- 每个应用关联一个"开发会话"
- 会话中保留 AI 生成的完整代码上下文
- 用户可以随时回到开发会话继续迭代
- 修改后重新发布，覆盖原 URL 或生成新版本

### 5.4 AI 代码生成质量保障

- **模板库**：常见场景（ECharts 图表、表格、表单）提供参考模板
- **API 文档注入**：将可用的业务 API 文档作为上下文提供给 AI
- **沙箱校验**：生成后在沙箱中运行校验，确保无语法错误
- **安全审查**：检查生成的代码不包含危险操作（XSS、外部请求等）

## 八、实施路径

### Phase 1：MVP — 静态 HTML 生成与发布

**目标**：跑通"对话 → 生成 HTML → 预览 → 发布 → 访问"全链路

- AI 生成自包含的 HTML 页面（数据内嵌，不调接口）
- 预览使用 iframe 沙箱
- 发布存储到本地文件系统 / PVC
- 应用市场展示已发布应用列表

**交付物**：
- 对话开发入口页面
- HTML 预览组件
- 发布 API + 存储
- 应用列表 API + 展示页面

### Phase 2：动态数据对接

**目标**：生成的页面可以调用真实 API 获取实时数据

- 发布服务增加 API 代理层
- AI 代码生成时注入 API 调用代码
- 接口白名单与权限控制
- 支持实时查询和定时刷新

### Phase 3：可复用卡片与仪表盘组装

**目标**：支持小颗粒度的卡片组件开发和仪表盘拼装

- 定义卡片规范（结构、尺寸、配置 schema）
- 支持发布为"卡片"类型
- 卡片库管理（浏览、搜索、分类）
- 仪表盘组装页面（拖拽布局 + 参数配置）
- 仪表盘发布为页面应用

### Phase 4：应用迭代与版本管理

**目标**：已发布的应用/卡片可以继续修改迭代

- 应用与开发会话关联
- 版本历史管理
- 回滚能力
- 应用分享与权限

### Phase 5：平台化能力

**目标**：形成通用的 AI 辅助应用开发平台

- 模板市场（常见场景模板）
- 组件库（可复用的图表、表格组件）
- 多用户协作
- 应用审批发布流程
- 访问统计与运营分析

## 九、可复用卡片组件（Widget）

### 7.1 概念定义

除了完整的页面应用，用户还可以通过自然语言创建**可复用的小卡片组件**。

| 维度 | 页面应用 | 卡片组件 |
|------|---------|---------|
| 颗粒度 | 完整页面 | 局部展示块 |
| 独立访问 | 有独立 URL | 可独立访问，也可嵌入其他页面 |
| 复用性 | 整体使用 | 可在多个地方重复使用 |
| 组合性 | 不可组合 | 多个卡片可拼装成仪表盘 |

### 7.2 典型卡片示例

- **告警 TOP10** — 按严重程度/频次排序的告警列表
- **最近待办工单** — 当前用户待处理的工单列表
- **CPU 使用率 TOP5** — 资源消耗最高的设备排行
- **今日巡检概览** — 巡检结果的通过/异常统计
- **设备在线率** — 各地市设备在线占比环形图
- **本周告警趋势** — 最近 7 天告警数量折线图

### 7.3 卡片特性

**小而独立**
- 固定尺寸规格（如 1x1、2x1、2x2 等网格单元）
- 自包含的 HTML/JS/CSS 片段
- 有明确的数据源和刷新策略

**可复用**
- 同一张卡片可以出现在多个位置：首页仪表盘、运营看板、Portal 侧边栏、大屏
- 支持参数化配置（如"告警 TOP N"中的 N 可配置）

**可组合**
- 用户选择多个卡片 → 拖拽排列布局 → 形成自定义仪表盘
- 仪表盘本身也可以作为"页面应用"发布

**实时数据**
- 卡片内 JS 调用后端 API 获取最新数据
- 支持自动刷新间隔配置

### 7.4 卡片与应用的关系

```
┌─────────────────────────────────────────────┐
│              用户自定义仪表盘                  │
```

产出物层级：
1. **卡片（Widget）** — 最小可复用单元
2. **仪表盘（Dashboard）** — 多个卡片的组合排列
3. **页面应用（App）** — 完整独立页面（可能包含仪表盘，也可能是独立逻辑）

### 7.5 卡片的开发与管理

**开发流程**（与页面应用一致）：
```
用户：帮我做一个告警 TOP10 的卡片，显示最近 24 小时最严重的 10 条告警
AI：[生成卡片 HTML，调用告警查询 API，列表展示]
用户：加上告警等级的颜色标识，紧急用红色，严重用橙色
AI：[修改卡片样式]
用户：发布为卡片
AI：[存储为可复用卡片组件]
```

**管理能力**：
- 卡片库：所有已发布卡片的列表
- 分类标签：按业务域分类（告警、工单、资源、性能）
- 参数配置：每个卡片支持可配置参数（刷新间隔、数据量、过滤条件）
- 尺寸规格：声明支持的网格尺寸

### 7.6 仪表盘组装

用户创建仪表盘时：
1. 从卡片库中选择需要的卡片
2. 拖拽到网格布局中，调整位置和大小
3. 配置各卡片的参数
4. 预览整体效果
5. 发布为仪表盘应用

也可以用自然语言：
```
用户：帮我做一个运维日常看板，包含告警 TOP10、待办工单、今日巡检概览和设备在线率
AI：[自动选取 4 个卡片，组装为 2x2 布局的仪表盘]
```

### 7.7 技术实现要点

| 要点 | 说明 |
|------|------|
| 卡片规范 | 定义标准的卡片 HTML 结构、尺寸声明、配置 schema |
| 隔离渲染 | 每个卡片在独立 iframe 或 shadow DOM 中渲染，避免样式/脚本冲突 |
| 通信协议 | 卡片与宿主页面通过 postMessage 通信（如通知刷新、传递参数） |
| 懒加载 | 仪表盘中卡片按可视区域懒加载，避免同时请求过多接口 |
| 统一刷新 | 仪表盘级别的全局刷新按钮，触发所有卡片重新加载数据 |

## 十、与已有方案的衔接

`html-artifact-publishing-service` 方案文档中描述的独立发布服务作为**远期演进目标**保留，适用于多系统接入、多租户隔离、海量应用管理等场景。

**当前阶段采用简化方案**：

- 不新增独立发布服务
- 发布的 HTML 直接存入共享存储，由前端 nginx serve
- 后端负责生成 HTML + 管理元数据
- 前端 nginx 的 `/artifacts/` location 直接对外提供访问

**远期演进路径**：

```
当前：后端写文件 → 共享存储 → 前端 nginx serve
远期：后端调 API → 独立发布服务 → 对象存储(MinIO/S3) → CDN/独立域名
```

当应用数量增长到需要独立管理（多租户、审计、CDN 加速）时，再将存储层从共享目录升级为对象存储 + 独立发布服务。架构切换对上层透明，只需修改后端的"写入目标"即可。

本方案新增的是"发布之前"的部分：

- 对话式需求输入
- AI 代码生成
- 实时预览与迭代
- 数据 API 对接

完整链路：**用户描述 → AI 开发 → 预览确认 → 写入共享存储 → nginx 直出访问**。
