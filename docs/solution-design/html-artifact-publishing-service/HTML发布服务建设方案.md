# HTML 成果发布服务建设方案

## 一、建设背景

当前轻应用、数据分析、智能助手等场景，越来越多地需要把运行过程中的结果直接输出为可视化页面，例如：

- 分析报告页面
- 图表展示页面
- 可分享的成果链接
- 可归档、可复用的专题页面
- 用户借助智能体，基于系统能力接口和查询结果二次开发出的展示页面

这些页面不是固定内容，而是业务运行过程中动态生成的成果。随着应用数量增加，如果缺少统一发布能力，成果页面的生成、保存、访问、分享、下线都会逐步演变为重复建设问题，影响整体交付效率、管理规范性和后续扩展能力。

尤其是在智能体逐步成为业务操作入口之后，用户并不只是“看现成页面”，还会希望借助智能体，调用现有能力接口、组织查询到的数据，快速二次开发出一个可直接展示的 HTML 页面。这类页面同样属于业务成果，也需要有统一、稳定、可管理的发布机制。

因此，有必要建设一项统一能力：**让后端底座服务生成的 HTML 成果，能够被标准化发布、稳定访问、统一管理。**

## 二、当前面临的主要问题

从业务和管理视角看，现阶段主要存在以下痛点：

| 问题 | 表现 |
| --- | --- |
| 发布方式不统一 | 不同场景各自处理成果页面，复用性差 |
| 职责边界不清晰 | 页面生成、页面托管、页面访问入口混在一起 |
| 成果不易沉淀 | 页面可访问、可分享，但缺少统一归档和管理 |
| 稳定性不足 | 一旦环境变化或服务重启，成果页面容易失效 |
| 扩展成本高 | 每新增一个场景，都要重复考虑“怎么发布页面” |

简单来说，现在缺的不是“能不能生成页面”，而是**缺少一套统一、稳定、可复制的成果发布机制**。

## 三、建设目标

本次方案希望解决的是“成果发布能力标准化”问题，核心目标如下：

1. **统一发布出口**：所有动态生成的 HTML 成果，都通过统一能力发布。
2. **统一访问方式**：对外提供稳定链接，方便查看、分享和沉淀。
3. **统一管理机制**：支持后续扩展到版本、归档、下线、清理等管理动作。
4. **降低场景接入成本**：业务场景只关注“生成成果”，不再重复建设“发布流程”。
5. **支撑用户二次开发**：支持用户借助智能体，基于系统能力接口和已查询数据，快速生成可展示页面。
6. **支撑平台化演进**：从单点场景能力，逐步演进为通用成果发布平台。

## 四、方案总体思路

建议新增一个独立的 **HTML 成果发布服务**，与现有前端门户、后端底座服务形成清晰分工：

- **后端底座服务**：负责提供能力接口、数据支撑并生成业务成果页面
- **HTML 成果发布服务**：负责接收成果、统一发布、统一存储、统一管理
- **前端门户**：负责展示成果入口、跳转访问，不承担成果托管职责

这套思路的核心价值在于：

> 把“内容生成”和“成果发布”拆开，让成果页面从临时产物变成标准资产。

这样做以后，业务侧看到的是“生成一个成果链接”，管理侧得到的是“一套可治理、可复制、可扩展的能力”。

这里的“内容生成”不只是系统内部固定流程生成报告，也包括用户借助智能体进行轻量二次开发：例如基于现有能力接口、业务查询结果或分析数据，快速组合出一个面向汇报、展示或专题分析的 HTML 页面。只要这类页面最终需要被访问、分享和沉淀，就应该纳入统一发布能力，而不是由每个场景各自处理。

进一步说，这个方案不是简单增加一个发布入口，而是把原本分散在不同场景里的成果处理动作统一收口：谁负责生成、谁负责发布、谁负责展示、谁负责后续管理，都有了清晰边界。这样可以避免不同团队各自采用临时办法处理成果页面，导致标准不一致、运维不可控、后续难以沉淀。

从建设逻辑上看，这项能力更适合作为底座能力统一建设，而不是跟着某一个具体业务场景走。原因在于，今天是 HTML 报表，明天可能就是专题分析页、巡检结果页、运营展示页，本质上都是“动态生成成果的统一发布”问题。如果这次方案能够按公共能力建设，后续新增场景就不需要再重复讨论发布方式，只需要接入这套统一机制即可。

从管理价值看，这种建设方式也更有利于形成长期资产。一方面，前端门户仍然保持“统一入口”的角色，不会因为承接运行时成果托管而变重；另一方面，后端底座服务也可以专注在生成能力本身，不需要同时承担长期托管职责。最终形成的是“生成归生成、发布归发布、展示归展示”的稳态架构，更适合后续持续扩展和规范治理。

## 五、为什么要独立建设发布服务

如果不单独建设发布服务，而是继续把成果页面挂靠在现有系统上，会带来三个问题：

### 1. 容易形成职责混乱

前端门户本质上应该负责展示和交互，不适合承接运行时成果托管；后端底座服务应聚焦生成能力，也不适合长期承担发布管理职责。

### 2. 不利于后续规模化扩展

今天可能只是报表页面，明天还可能有专题分析页、自动巡检报告、场景复盘页、运营看板页。如果没有统一发布能力，后续每扩一个场景都要重新造轮子。

### 3. 不利于成果资产化管理

领导视角更关心的是：这些成果能否稳定访问、是否便于沉淀、后续能否纳入统一管理。独立发布服务天然更适合承接这类能力。

## 六、结论与建议

这项建设的本质，不是单纯新增一个页面服务，而是补齐一项关键基础能力：

> **让动态生成的业务成果，具备统一发布、稳定访问、持续沉淀的能力。**

建议结论如下：

1. **同意立项建设 HTML 成果发布服务**
2. **按公共能力方式推进，而不是按单一场景临时开发**
3. **第一阶段聚焦闭环打通，尽快形成可用成果**
4. **后续根据业务使用情况，再逐步增强治理和运营能力**

如果这项能力建设到位，后续无论是报表、分析页、巡检结果页，还是面向客户和管理层的专题成果页，都可以通过同一套机制快速交付，长期收益明显高于一次性开发成本。

更重要的是，这项能力还能支撑用户围绕现有系统做更灵活的二次开发：用户可以借助智能体，调用平台已有能力接口、复用已有数据查询结果，快速产出一个可展示的页面，再通过统一发布服务形成稳定成果链接。这样既放大了底座能力的价值，也降低了用户创新和场景落地的门槛。
