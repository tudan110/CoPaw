# 面向客户的自然语言定制能力方案

## 1. 背景

当前产品基于 **QwenPaw** 作为运行底座，定制前端在 `portal/`，定制后端在 `src/qwenpaw/extensions/`，原则上 **不改动 QwenPaw 主干代码**。

业务诉求不是让客户拿源码自行开发，而是让客户在产品部署到其服务器后，能够通过**自然语言**提出定制需求，由系统在受控边界内自动生成配置化能力并发布。

## 2. 方案定位

本方案的核心不是：

> 自然语言 -> 自动写代码 -> 客户自己二开

而是：

> 自然语言 -> 结构化意图 -> 配置化资产 -> 复用现有能力 -> 预览/审批/发布

其中：

- **Markdown**：用于需求摘要、方案说明、审批材料、审计留痕
- **YAML / JSON / TOML**：用于系统真实执行配置
- **Skill / 定时任务 / 连接能力 / Portal 配置**：作为底层复用能力块

## 3. 目标与非目标

### 3.1 目标

- 支持客户通过自然语言描述定制需求
- 自动复用现有 Skill、定时任务和系统接入能力完成装配
- 自动生成页面、权限、流程、调度等配置资产
- 支持预览、审批、版本管理和回滚
- 保持客户无源码、无代码开发门槛

### 3.2 非目标

- 不向客户开放产品源码
- 不让客户直接编写 Skill 代码
- 不允许客户修改 QwenPaw 核心运行逻辑
- 不承诺所有需求都能自动化实现

## 4. 总体思路

客户输入的是**业务需求**，系统生成的是**可执行配置**。

典型链路如下：

1. 客户输入自然语言需求
2. AI 将需求解析为结构化意图
3. 系统匹配已有 Skill 模板和能力块
4. 生成可执行配置和说明文档
5. 客户或实施人员预览确认
6. 通过审批和门禁后发布到客户实例
7. 保留版本、差异和回滚能力

## 5. 结构化意图模型

自然语言不直接驱动代码，而是先收敛为结构化模型，例如：

| 字段 | 示例 |
|---|---|
| 场景类型 | 巡检 / 告警 / 工单 / 报表 |
| 目标对象 | Oracle / MySQL / 主机 / 应用 |
| 触发方式 | 手动 / 定时 / 告警触发 |
| 执行动作 | 查询 / 汇总 / 通知 / 建单 |
| 风险等级 | 只读 / 写入 / 生产变更 |
| 审批要求 | 无 / 单人 / 双人 |
| 展示位置 | 首页卡片 / 菜单页 / 助手入口 |

这层结构化意图是系统内部的中间表示，也是后续生成配置的统一输入。

## 6. 底层能力复用方式

### 6.1 Skill 的定位

现阶段仍以 Skill 作为主要能力复用单元，但对客户应隐藏其实现细节。客户看到的是“新增一个能力”，不是“新增一个 Skill 项目”。

更适合的做法是把已有 Skill 抽象成**场景模板**，例如：

- `inspection-analyst`
- `alarm-analysis`
- `workorder-dispatch`

客户自然语言定制时，本质上是：

> 选择已有 Skill 模板 + 填充参数 + 绑定系统 + 生成配置

### 6.2 外部系统调用能力

当前如果外部系统接入逻辑主要内嵌在 Skill 中，短期可继续沿用；中期建议逐步抽成可复用连接能力，例如：

- CMDB 查询
- 监控告警查询
- ITSM 建单
- 企业微信/短信通知

这些连接能力可以先在 `src/qwenpaw/extensions/` 中以内部 service/adapter 形式沉淀，后续再根据复用度评估是否进一步 MCP 化。

### 6.3 Portal 的定位

Portal 负责承载客户可见的定制结果，例如：

- 菜单和入口
- 首页卡片和报表
- 交互动作和跳转
- 配置预览和发布确认界面

## 7. 生成资产类型

系统应优先生成配置型资产，而不是源码。

| 类别 | 产物 |
|---|---|
| 场景能力 | 复用既有 Skill 模板并生成参数配置 |
| 调度 | 定时任务配置 |
| 页面 | Portal 菜单、卡片、按钮、跳转配置 |
| 权限 | 角色可见范围、审批规则、风险边界 |
| 连接 | 客户系统接入参数绑定 |
| 文档 | 方案说明、风险说明、验收清单 |

示例：

```yaml
scenario: oracle_inspection
trigger:
  type: schedule
  cron: "0 8 * * *"
capabilities:
  skill: inspection-analyst
  target: oracle
  notify: wecom
  ticket: itsm_create
policies:
  allow_write: false
  allow_production_change: false
portal:
  menu: 数据库巡检
  card: Oracle巡检结果
```

## 8. 示例场景

### 8.1 巡检能力定制

客户输入：

> 给我一个 Oracle 巡检助手，每天 8 点执行，异常自动建单，但不能自动变更。

系统生成：

- 复用 `inspection-analyst` 模板
- 一份 Oracle 巡检参数配置
- 一条定时任务
- 一份工单动作配置
- 一份禁止自动变更的安全策略
- Portal 入口和结果卡片

### 8.2 首页定制

客户输入：

> 首页加一个待处理工单卡片，领导只能看汇总，运维能看明细。

系统生成：

- Portal 卡片配置
- 不同角色的数据展示规则
- 卡片跳转动作
- 菜单和权限配置

### 8.3 流程编排

客户输入：

> 收到 P1 告警时，先查 CMDB 负责人，再自动建 ITSM 工单。

系统生成：

- 告警处理场景配置
- CMDB 查询能力绑定
- ITSM 建单动作绑定
- 对应审批与日志策略

## 9. 边界定义

### 9.1 可通过自然语言自助完成

- 新增巡检、查询、报表、告警分析类能力
- 页面、菜单、卡片、报表样式调整
- 定时任务、通知规则、审批规则调整
- 已有系统连接器的参数绑定和流程组合

### 9.2 不适合完全自助完成

- 新外部系统的底层接入开发
- 高危生产动作自动化
- 核心鉴权、调度、运行引擎改造
- QwenPaw 主干代码修改

超出边界时，系统应明确提示进入厂商实施流程，而不是继续尝试自动生成。

## 10. 安全与发布要求

自然语言定制不能直接生效，必须经过受控发布流程：

1. 配置预览
2. 权限与风险检查
3. 敏感动作识别
4. 审批流
5. 版本发布
6. 回滚能力校验

建议所有定制动作都具备：

- 版本号
- 差异对比
- 发布记录
- 审批记录
- 回滚记录

## 11. 技术落位建议

### 11.1 `portal/`

负责：

- 客户自然语言输入入口
- 结构化预览页面
- 配置确认和发布界面
- 历史版本和回滚界面

### 11.2 `src/qwenpaw/extensions/`

负责：

- 自然语言需求解析
- 结构化意图建模
- Skill 模板匹配
- 配置生成
- 审批和发布编排
- 版本与审计管理

### 11.3 QwenPaw 底座

负责：

- 运行已生成的 agent / skill / scheduler / portal 配置
- 提供稳定运行时能力
- 避免承载客户定制逻辑本身

## 12. 实施建议

### MVP 1：自然语言生成配置

- 生成 Agent/Portal/调度/权限配置
- 复用现有 Skill 模板
- 实现预览和确认

### MVP 2：自然语言场景编排

- 将通知、建单、查询、报表串成配置化流程
- 增加角色和审批规则

### MVP 3：连接能力沉淀

- 从 Skill 中抽取通用系统调用
- 形成内部可复用 adapter/service
- 对复用度高的能力再评估 MCP 化

## 13. 结论

本方案的核心结论是：

> 不让客户开发代码，而让客户用自然语言提出需求；  
> 系统将其转成结构化配置，复用现有 Skill、定时任务和系统连接能力完成装配；  
> 最终通过预览、审批、发布、回滚的完整链路，把客户需求落成受控的产品能力。

这是一套**自然语言驱动的受控定制平台方案**，而不是源码级二开方案。
