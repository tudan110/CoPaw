# 自动根因分析产品介绍

## 1. 产品定位

自动根因分析（Automatic Root Cause Analysis，RCA）是 QwenPaw 故障分析专家面向活动告警和应用故障现象提供的一套智能诊断与处置闭环能力。

它的目标不是简单地“查告警”或给出一条经验性的故障结论，而是把告警、资源、拓扑、变更和性能指标组织成一条可追溯的证据链，回答四个问题：

1. 到底发生了什么故障？
2. 最可能的根因在哪个资源、哪一层？
3. 故障影响了哪些上游业务和用户？
4. 现在应该如何止血、修复，并确认业务已经恢复？

产品以 `alarm-analyst` skill 为核心编排逻辑，支持数据库、网络、IaaS、PaaS、应用以及机房动环等场景，也支持从“某应用新增数据失败”“CMDB 插入失败”等业务现象反向下钻分析。

## 2. 从告警到闭环的整体流程

```text
活动告警/业务故障现象
        ↓
告警解析与资源识别
        ↓
告警上下文 + CMDB资源 + 应用/基础设施拓扑
        ↓
变更关联 + 拓扑关联告警 + 性能指标
        ↓
六步分析法：识别 → 变更 → 拓扑 → 指标 → 根因 → 影响
        ↓
根因判断、置信度、影响范围与候选根因
        ↓
先止血后修复的处置建议
        ↓
报告/通知推送 → 恢复验证 → 清除告警 → 状态回写
```

### 2.1 告警自动接入

系统支持两类入口：

- **活动告警入口**：用户在 Portal 中从右上角铃铛选择告警，故障分析专家接管该告警。
- **故障现象入口**：用户直接描述应用不可用、数据写入失败、数据库锁异常等现象，系统先定位相关应用或资源，再按同一套 RCA 流程分析。

接入后首先抽取并确认告警标题、告警编号、资源 ID/CI ID、设备名称、管理 IP、告警时间、资源类型和严重级别。这些字段是后续查询和报告关联的主键，不能依赖模糊文本替代。

告警上下文来自智观活动告警数据。系统会围绕事件时间查询当前活动告警及近期开历史告警，并在本地按资源 ID 过滤，避免把同一时间窗内其他设备的告警误归入当前故障。

## 3. 先确认资源，再理解故障位置

告警只说明“哪里出现了异常”，不一定说明“哪里是根因”。因此系统会先查询 CMDB：

- 获取根资源详情，确认资源名称、CI 类型、管理 IP 等身份信息；
- 获取资源的上下游关系和承载关系；
- 从应用拓扑拆解数据库、中间件、网络、主机、容器等依赖组件；
- 将资源关系转换为影响链，识别可能的故障源头和受影响对象。

拓扑分析遵循“从业务向下拆解、从异常向上回溯”的方式。例如“应用新增数据失败”不会停留在应用层，而会继续检查应用依赖的数据库、连接池、消息队列、主机资源和网络路径；“数据库写入失败”也会反向检查存储、主机磁盘、网络和近期变更。

当存在拓扑数据时，分析报告会输出 ECharts 拓扑图。默认采用从左到右的树形结构展示依赖层级；复杂的多对多关系才使用网状图，并高亮根因资源和受影响节点。

## 4. 六步分析法

六步分析法是所有场景共用的 RCA 主流程，保证分析过程可解释、可复核。

| 步骤 | 分析内容 | 关键产出 |
|---|---|---|
| 1. 告警识别 | 识别告警类型、对象、时间、级别和初始故障现象；告警风暴时先按时间和空间聚合去噪 | 故障初始线索、分析对象 |
| 2. 变更关联 | 检查故障前 24 小时内的配置变更、版本升级、发布、割接和参数调整 | 变更命中情况；命中时作为高优先级根因线索 |
| 3. 拓扑关联 | 关联网络、IaaS、PaaS 和应用拓扑，确定上下游依赖、承载关系和传播路径 | 根因候选资源、影响范围 |
| 4. 性能指标分析 | 查询资源类型对应的指标定义，再筛选相关指标，分析当前值、历史趋势、阈值和动态基线偏离 | 异常指标及异常说明 |
| 5. 根因判定 | 融合告警、变更、拓扑和指标证据，按照时序先后、证据数量、变更命中和偏离幅度排序候选根因 | 主根因、Top-N 候选根因、置信度 |
| 6. 影响评估 | 结合业务等级、受影响用户/应用、冗余和备份状态评估爆炸半径与紧急程度 | 影响范围、优先级、处置策略 |

其中，时序关系是重要判断依据：通常先出现异常的资源更接近故障源头，后出现的应用报错更可能是传播结果。对于告警风暴，系统先收敛“最早异常对象”和共享依赖，避免把一条故障传播链误判成多个独立故障。

指标分析同时支持固定阈值和动态基线。固定阈值用于识别 CPU、磁盘、锁等待、丢包等明显异常；动态基线用于识别尚未越过阈值、但相对历史同环比已明显劣化的情况。

## 5. 拓扑驱动的关联告警分析

拓扑不是报告中的装饰图，而是 RCA 的必要数据。拿到根资源拓扑后，系统会提取根资源、拓扑节点以及关系边上的全部资源 ID，再逐一查询这些关联资源在相同时间窗口内的告警。

这样可以识别典型的传播模式：

- 网络链路异常 → 主机连接异常 → 数据库连接中断 → 应用接口超时；
- 存储 I/O 延迟升高 → 数据库慢查询增加 → 连接池耗尽 → 数据写入失败；
- 主机资源耗尽 → 容器驱逐或进程异常 → 中间件不可用 → 上游业务失败；
- 共享依赖异常 → 多条业务链同时异常，形成级联故障。

如果关联资源告警没有全部查询完成，报告必须标记为 `partial`，降低分析置信度，不能宣称已经完成完整 RCA。只有在证据采集完成后，系统才进入综合判断阶段。

## 6. 面向多层故障场景的分析能力

系统按故障所在层次加载对应的场景知识和判定规则：

- **机房动环层**：供配电、UPS、精密空调、温湿度、漏水、消防、门禁和动环采集器；
- **网络层**：物理链路、设备故障、时延/丢包、配置错误、路由震荡、二层环路、IP 冲突和 DHCP；
- **IaaS 层**：硬件、虚拟化、存储、操作系统、资源耗尽、时钟同步、进程与服务；
- **PaaS 层**：容器编排、中间件、服务网格、数据库与缓存、配置证书、云主机、负载均衡和网关；
- **应用层**：代码缺陷、业务逻辑、依赖服务、API、拨测不可用、响应劣化、局部功能异常、前端问题和流量并发；
- **跨层故障**：级联故障、网络-应用联合故障、IaaS-PaaS 联合故障和全链路退化。

这套分层知识库让系统能够把“故障现象”映射到专业领域，再结合真实数据进行判断，而不是只根据告警标题做关键词匹配。

## 7. 根因结论与证据链

报告会给出：

- 主根因及其所在资源；
- 故障性质和根因方向；
- 关键告警、指标、拓扑和变更证据；
- 根因置信度；
- 多个可能性并存时的 Top-N 候选根因；
- 与当前告警存在因果关系或强相关性的异常指标。

若数据源不可用、返回空数据或某个查询失败，系统遵循“单次尝试、如实记录、继续分析”的原则：将该环节标记为部分完成，继续利用其他证据完成降级分析，不通过反复切换参数来凑结论，也不伪造已执行结果。

## 8. 影响范围与处置策略

处置建议采用“先恢复业务、再根治根因”的双轨原则。系统会先判断业务等级、影响用户范围、是否有冗余、预期恢复时间以及动作风险，再决定是否启用紧急预案。

- **影响范围大**：核心业务、大面积用户受影响或无可用冗余时，建议第一条必须是紧急止血动作，例如切换备用链路/节点、主备倒换、流量迁移、熔断降级、限流隔离、回滚近期变更或启用备用电源/制冷；之后再安排根因修复。
- **影响范围可控**：存在有效冗余、属于边缘单点或仅影响单用户时，直接给出根因修复动作，避免增加不必要的操作步骤。

重启、割接、换件、配置下发、删除和主从切换等高风险动作只作为建议输出，并明确“需人工确认审批后执行”。数字员工负责分析、编排和验证，不越权执行高风险操作；工单也不在分析过程中未经用户确认自动创建，而是在 Portal 中以可确认的工单提议呈现。

## 9. Portal 交付与故障闭环

分析结果会形成结构化的 Portal 告警分析卡片和 Markdown 报告，包含告警基础信息、拓扑、根因判断、影响范围、异常指标、处置建议、自动化执行结果以及恢复验证结果。

在 RCA 结论形成后，系统推送分析报告和通知；处置完成后执行恢复验证，观察告警是否恢复、相关指标是否回落、业务是否重新可用，然后再清除告警并回写状态。Portal 卡片还可以承载工单提议、工单状态、证据列表和处置阶段，方便值班人员继续跟进。

最终总结至少回答：置信度、故障性质、根因方向、影响范围、紧急预案、优先动作、关联资源告警查询状态和通知状态。

## 10. 当前能力边界与演进方向

当前 RCA 已经能够基于告警、指标、CMDB 拓扑和变更信息完成资源级、跨层级的根因收敛。对于服务级调用传播，当前尚未接入 APM 调用链，因此可以根据各层告警、指标和业务-资源映射进行推断，但不能把缺少 APM 证据的调用级传播描述为完全确认。

后续可以继续增强：

- 接入 APM 调用链，补齐服务到服务的精确传播路径；
- 沉淀历史故障案例和处置结果，形成可复用的根因模式库；
- 引入更完善的动态基线和容量趋势预测；
- 将恢复验证结果反哺根因置信度和处置策略；
- 在人工确认机制下扩展低风险自动修复和工单闭环。

## 11. 一句话总结

自动根因分析的核心做法，是把“告警触发”升级为“基于拓扑和证据的故障推理”：先自动接入并确认告警资源，再沿依赖拓扑扩展关联告警，结合变更和指标按六步分析法收敛根因，评估影响范围，给出先止血后修复的建议，最后通过通知、恢复验证、清警和状态回写完成故障闭环。
