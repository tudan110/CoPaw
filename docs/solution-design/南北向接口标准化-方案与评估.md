# 南北向接口标准化 · 方案与风险评估

> **一句话概括**:在系统正中间插入一个"能力层"——对下让各种数据源即插即用,对上让大屏、对话统一取数。系统由此从"专门对接智观的产品"升级为"可承接任意数据源的能力底座"。

> 状态:方案评审稿(待决策)  ·  读者:决策层 + 技术评审  ·  日期:2026-07-08

---

## 0. 执行摘要

**要解决什么问题。** 当前系统把"业务能力(查告警、查流量、查 CMDB)"和"对接智观系统的具体接口(URL、字段名、认证)"焊死在同一段代码里,分散在几十处。结果是:换一个数据源(交付到客户现场、客户用的不是智观)几乎等于重写;同一份逻辑在系统里存在多份副本,改一处漏一处,已经造成过"对话和大屏显示不一致"的线上问题。

**建议怎么做。** 引入一个**能力层**,把"要什么数据(能力契约)"和"去哪拿、怎么翻译(连接器)"彻底分开。新接一个系统 = 装一个"连接器插件" + 做一次字段映射,**不改上层业务**。规整的系统可做到零代码接入,接口古怪的系统只写差异部分。

**投入与节奏。** 采用**绞杀式改造**(不停机、不大爆炸重写),分 5 个阶段推进。**每个阶段结束都有可用、可回退的状态**,第一阶段只定标准、不碰业务代码,风险极低,可作为"试水"决策点。整体量级见第 6、7 节(需团队按实际人力细化排期)。

**最大的三个风险,是否可控。**
1. *改动现有取数链路,可能弄坏已上线的大屏/对话* → 有现成的大屏回归记分器 + 灰度双跑兜底,**可控**。
2. *数据标准由谁定、会不会扯皮* → 标准不是凭空设计,而是从现有三处已有代码反推归并,**有客观依据,可控**。
3. *客户字段千奇百怪,映射层复杂度失控* → 只标准化"真正的共性字段",其余原样透传;有第二数据源需求的能力才做标准化,**范围可控**。

**需要决策的事项(详见第 8 节)。** ①是否立项及优先级;②投入的人力与周期;③是否接受"先小步验证、再决定是否加大投入"的节奏;④"对外开放接口"这个可选未来方向,现在是否要纳入范围。

**为什么现在做划算。** 系统已经自发长出了这套架构的三个雏形(见第 3 节),地基已在;本项目是把它们补齐、让核心业务迁移上去,**不是从零另起炉灶**。同时,它顺带根治了"多副本不一致"这一类反复出现的线上问题。

## 1. 背景与目标

### 1.1 现在的样子

系统目前对接的是内部的**智观(INOE)系统**,通过一系列"技能"和后端集成模块,查询告警、流量、CMDB、工单、日志等。这些对接是**点对点硬编码**的:代码里直接写着智观的接口地址、字段名、认证方式。

### 1.2 想要达成的样子

用户提出的目标是**"南北向接口标准化,把整个系统当作一个能力底座"**:今后任何系统的接口数据要接入,都能像插头一样即插即用。典型场景——**交付到客户现场,客户用的告警/流量系统不是智观,但我们的大屏和对话应该照常工作,只需换一个"数据源插头"。**

### 1.3 三个目标词的准确含义

用户用了三个词,评审时容易各自理解不同,这里对齐(详细见第 2 节):

| 用户的说法 | 准确含义 | 是否本项目主线 |
|---|---|---|
| 标准化南向能力 | 让**数据源可插拔**:换个系统提供数据,上层不用改 | ✅ **主线** |
| 北向接口整理收口 | 让**内部消费方**(大屏/对话/Portal API)统一走一个取数入口 | ✅ 主线的一部分 |
| 能力底座 | 系统本身成为中台;**别人反过来调用我们**的能力 | ⚪ 可选未来,非当前必须 |

## 2. 术语对齐

"南向 / 北向"是电信网管领域的行话,套到本系统上需要翻译,否则评审会各说各话。

- **南向(朝下)**:我们的系统作为**消费者**,去调别人拿数据。我们调智观的告警、流量,都是南向。**这是本项目的主战场。**
- **北向(朝上)**:别人作为**上层系统**,来调用我们。这里要拆成两半:
  - **内部消费方**(大屏应用、对话应用):它们在消费数据,但它们是我们系统**自己的模块**,不是外部系统。准确说它们不是"对外北向接口",而是"内部消费方"。用户说的"北向整理收口",实际指的是**把这些内部消费方的取数方式统一收口**。
  - **对外北向接口**(客户的另一套平台来调我们):**目前系统里基本不存在**。这是能力层建成之后可以自然开出去的口子,属于**可选的未来产品化方向**,不是当前刚需。
- **能力底座**:上述能力层建成后系统呈现出的形态——对下接万源、对上供多方。

> **一句话对齐**:本项目做的是"在系统中间插一层能力层"。对下,让数据源即插即用(南向标准化);对上,让内部消费方统一取数(内部收口);"别人来调我们"(真北向)是这层做好后可选的开放接口。**一层,同时回应三个诉求。**

## 3. 现状评估(基于代码调研,可逐条核对)

以下结论来自对仓库的系统性调研,均可对照代码核实。

### 3.1 好的地基:已有一层收敛,且有三个现成雏形

**这决定了本项目是"补齐升级"而非"推倒重来"。**

1. **配置(控制平面)已经收敛。** 所有外部系统的连接配置(地址、令牌)已统一到单一数据源 `settings.db`,通过字段规格(`FieldSpec`)+ 物化机制注入。这一层是干净的、和业务解耦的。→ 本项目**无需重做配置层**。
2. **大屏能力目录**(`ai_big_screen/capabilities`)已有"能力描述符 + 字段目录(canonical key/label/别名)"的结构,这正是"能力契约"的雏形。
3. **代理数据源(proxy datasource)**已有"URL 模板 + 认证 + 声明式字段映射(`rows_path`/`fields`) + SSRF 安全护栏"的机制,这正是"声明式连接器"的雏形。
4. **技能背书能力**(`skill:` 前缀)与代理能力(`proxy:` 前缀)已有"按前缀分派到不同实现"的机制,这正是"能力路由注册表"的雏形。

**关键判断**:方案不是发明新范式,而是把这三个已存在但只用于"边缘/动态数据源"的雏形,**提级为一等公民,并让核心业务(智观)迁移上去**。

### 3.2 痛点一:接口焊死在业务里(三层职责纠缠)

以告警查询脚本为例,一个函数里混着三种本该分开的职责:

| 职责 | 例子 | 换数据源时 |
|---|---|---|
| **业务/领域逻辑** | "没指定时间就默认查最近 24 小时"、"把'数据库'理解成一类资源" | 不变,与对接谁无关 |
| **接口适配** | 智观接口路径、字段名 `alarmSeverity`/`isClear`、Bearer JWT 认证 | **全变** |
| **数据归一** | 把智观返回的原始 JSON 翻译成标准告警行 | 需重写映射 |

这三样纠缠在一起,导致"换数据源"必须动到业务逻辑,牵一发动全身。

### 3.3 痛点二:同一份逻辑存在"2×N 份"

- **横向两份**:面向对话的"技能脚本"和面向大屏/Web 的"后端集成模块",对同一个智观接口**各写了一遍**(有代码注释直言,是为了"对齐两边显示"而刻意维护两份平行实现)。
- **纵向 N 份**:同一个技能因为部署隔离需要,在多个工作区里**逐字节复制**(告警技能 3 份、CMDB 技能 5 份)。

> **重要且公允的判断**:这些重复有**合理的历史原因**——对话与 Web 两个场景的性能/交互诉求不同;工作区副本换来的是部署隔离。**重复本身不是最紧急的问题**(不改就不会坏)。真正会咬人的是:**告警"长什么样"在多处各自定义,会漂移,导致"对话和大屏显示不一致"这类线上问题**。本项目通过统一标准根治这个病根,消除重复只是**顺带的副产品**——不应把"消除重复"当作立项的主要理由。

### 3.4 现状小结

- **控制平面(连接配置)**:已统一。✅
- **数据平面(查询实现 + 字段语义)**:分散、重复、与业务焊死。❌ ← **本项目的靶心**

## 4. 目标架构

### 4.1 总览

```
┌─ 内部消费方 ──────────────────────────────────────────────────┐
│   对话技能        Portal API         AI 大屏      (未来)对外接口 │
└──────┬───────────────┬─────────────────┬────────────────┬──────┘
       └───────────────┴────────┬────────┴────────────────┘
                    ┌────────────▼─────────────┐
   能力层入口        │  invoke_capability(能力, 参数)             │
   (统一收口)        │  统一信封 · 缓存 · 超时 · 遥测 · 状态裁决  │
                    └────────────┬─────────────┘
        ┌────────── 能力契约(标准"插座") ──────────┐
        │ alarm.query  metric.query  cmdb.ci.query  │
        │ ticket.query  log.search  ...             │
        │ 每个能力 = 标准参数 + 标准返回行(普通话)  │
        └────────────┬──────────────────────────────┘
                    ┌▼─ 能力路由注册表 ─┐
                    │ 已装连接器 → 能力  │  + 真探活状态
                    └─┬────┬────┬────┬──┘
      ┌───────────────┘    │    │    └───────────────┐
┌─────▼─────┐      ┌───────▼──┐ ┌▼────────┐   ┌──────▼──────┐
│ 智观连接器 │      │ CMDB连接器│ │夜莺连接器│   │客户XX连接器  │
│ (代码式)   │      │ (代码式)  │ │(代码式) │   │(声明式·YAML) │
└─────┬─────┘      └────┬─────┘ └───┬─────┘   └──────┬──────┘
   智观网关          Veops CMDB    夜莺           客户 XX 系统(南向)
```

### 4.2 四个核心概念

1. **能力契约(标准"插座")**:按领域定义标准能力,每个能力有**标准参数**和**标准返回行**两份 schema。例如 `alarm.query` 规定"告警行必须有 `severity`(值域 critical/major/minor/warning)、`occurred_at` 等"。厂商特有字段进 `extras` **原样透传,不丢失**。
   - **标准从哪来**:不是凭空设计,而是从现有三处归一化代码归并反推(见第 3.1)。

2. **连接器(标准"插头")**:一个外部系统一个连接器包,用清单声明"我实现了哪些能力、需要哪些配置、怎么认证、怎么探活"。两种实现档次:
   - **声明式(YAML 映射)**:规整的 REST 系统零代码接入——一份配置写完地址模板、参数/返回字段映射(含值映射,如 `P1→critical`)。这是把现有代理数据源机制泛化到所有能力域。
   - **代码式(Python)**:处理登录换令牌、多步请求、古怪参数等。共享的 HTTP 客户端、重试、认证插件由基类提供(把散落 5 处的"请求+回退"代码收敛成唯一一份)。

3. **连接实例**:连接器 + 一份配置 = 一个实例,支持**同类型多实例**(客户有两套监控系统)。生命周期:已配置 → **真探活通过** → 启用。

4. **统一信封**:所有取数返回统一结构 `{状态(live/empty/failed/gap), 数据行, 列定义, 元信息}`。大屏现有的"状态裁决"逻辑已是此形态,提级到平台层供三个消费方共用,**保证"没数据"和"出错了"被诚实区分**,不再出现假数据。

### 4.3 与 MCP 的关系

会有人问:"这不就是 MCP 吗,用 MCP 不就行了?" —— **方向类似,但统一的层次不同:**

- **MCP 统一的是"调用协议"**(怎么发现工具、怎么传参),属于**传输层**标准。它**不管**返回的数据字段叫什么、值是什么。
- **本方案统一的是"数据语义"**(告警必须有 severity 且值是标准词),属于**数据模型层**标准。

**为什么必须多统一这一层**:下游是大屏组件、Portal 表格、评测基线,它们要渲染"严重程度""发生时间"这些确定的列,**必须有确定的字段**。只有 MCP 的话,客户系统返回 `{"级别":"P1"}`,大屏不知道该画到哪、"P1"是什么级别。所以"转接层"干的不只是协议转换,**更是语义映射(`级别`→`severity`、`P1`→`critical`)**——这才是即插即用的真正价值与护城河。

**MCP 的正确定位**:它是连接器的**一种接入形态**(客户已有 MCP server 时,用"MCP 桥连接器"接入省事),但接进来后**仍要过语义映射**才能供大屏使用。MCP 是可选零件,不是架构本身。

## 5. 即插即用在客户现场的样子(业务/交付价值)

| 客户系统情况 | 接入方式 | 工作量 |
|---|---|---|
| 常见系统(Zabbix / Prometheus / 夜莺等) | 装现成连接器,填地址凭据,探活 | **零代码,分钟级** |
| 私有系统但接口规整 | 复制模板写一份 YAML 映射,热装载 | 半天,**不碰平台代码** |
| 接口古怪(多步认证 / 非标分页) | 写代码式连接器(基类兜底,只写差异) | 1–3 天,只写差异部分 |
| 客户已有 MCP server | MCP 桥连接器挂上 + 做语义映射 | 配置级 |

连接器的打包/安装**直接复用现有技能市场的 zip 安装机制**(路径穿越、zip 炸弹等安全防护都是现成的),无需新建分发通道。

## 6. 实施路线(绞杀式,分阶段,每步可回退)

**核心原则:不停机、不大爆炸重写。** 老链路继续跑,新能力层旁边长出来,一个能力一个能力地把消费方切过去,随时可回退。

| 阶段 | 目标 | 结束时的可用状态 | 可回退性 | 相对投入 |
|---|---|---|---|---|
| **M0 定契约** | 告警/指标/CMDB 三域的标准 schema、统一信封、连接器清单规范、注册表骨架 | 产出文档 + schema 文件,**不动业务代码** | 无需回退(未改代码) | 轻 |
| **M1 第一个插头** | 把智观重构为第一个连接器,现有集成模块改为其实现体 | 现有大屏/对话/Portal API **无感切换到新架构** | 保留旧路径,开关切回 | 中 |
| **M2 第二个插头(验证抽象)** | 接入真正的第二个数据源(如夜莺 + 一个演示用 mock 连接器);改造告警技能走能力层 | **可对客户演示"换数据源,大屏和对话照常工作"** | 新源独立,不影响智观 | 中 |
| **M3 平台化** | 设置页改造成"连接管理"(装→配→测→启用)、声明式 YAML 引擎、连接器打包安装、探活状态面板 | **交付工程师不写代码即可接标准系统** | 增量功能,不改已切换的链路 | 重 |
| **M4 生态(可选)** | 连接器 SDK + 脚手架、MCP 桥、对外开放北向接口 | 客户上层系统可反向消费我们的能力 | 纯新增 | 轻–中 |

> **投入说明**:上表为**相对量级**,非承诺排期。精确人天需团队按实际人力(建议至少 1 名后端为主 + 前端配合)细化。

**关键里程碑的决策价值**:
- **M1 结束** → 拿到"现有功能跑在新架构上、零回归"的信心。
- **M2 结束** → 拿到"真的能换数据源"的实证(**一个抽象只有一个实现等于没验证,两个实现才算数**),可对客户/领导演示。
- **M3 结束** → 达成"即插即用"的产品化目标。
- **M4** → 视商业需要决定是否开放对外。

## 7. 风险评估(核心章节)

| # | 风险 | 影响 | 概率 | 等级 | 缓解措施 |
|---|---|---|---|---|---|
| R1 | **改动现有取数链路,弄坏已上线的大屏/对话** | 高 | 中 | 🔴 高 | 绞杀式改造,老链路保留;用现有大屏回归记分器做每步回归;M1 灰度双跑对比新老输出一致再切 |
| R2 | **数据标准定义分歧/扯皮**(谁说了算) | 中 | 中 | 🟡 中 | 标准从现有三处已有代码**反推归并**,有客观依据;先做 3 个域不贪多;标准文件化、版本化、单一 owner |
| R3 | **映射层复杂度失控**(客户字段千奇百怪) | 中 | 中 | 🟡 中 | 只标准化真正的共性字段,其余进 `extras` 透传;**只对"有第二数据源可能"的能力做标准化**,专有能力不强塞 |
| R4 | **抽象只有一个实现 = 白抽**(过度设计) | 中 | 中 | 🟡 中 | M2 强制接入第二个数据源来验证;标准由消费侧真实用例反推,不按厂商 API 一比一切 |
| R5 | **多一层抽象带来性能开销** | 低 | 低 | 🟢 低 | 能力层是进程内函数调用,非新增网络跳;沿用现有多级缓存;探活/取数超时可配 |
| R6 | **技能子进程改走本机能力入口**引入的认证/治理问题 | 中 | 中 | 🟡 中 | 该步(M2)单独处理本机回环认证与治理放行,**不阻塞 M1**;先验证治理规则再切 |
| R7 | **人力/周期超预期** | 中 | 中 | 🟡 中 | 分阶段、每阶段独立交付价值;M0 极轻可先试水;可在 M1/M2 后重估是否继续 |
| R8 | **跨模块协调成本**(动到技能、大屏、Portal 三块) | 中 | 中 | 🟡 中 | 消费方逐个切换,不要求同时改;先切进程内的集成模块(易回归),技能子进程延后 |

**总体风险判断**:最高风险 R1(弄坏现有功能)有成熟的回归 + 灰度手段兜底,**可控**。其余为中低风险,均有明确缓解路径。**没有识别到"不可逆、会造成系统性损失"的风险**——这得益于绞杀式改造每步可回退的特性。

---

## 8. 需要领导决策的事项

1. **是否立项、优先级排序。** 相对当前其他工作,本项目的优先级?
2. **投入的人力与周期。** 是否投入(建议至少 1 后端 + 前端配合),投入到哪个阶段为止先复盘?
3. **是否接受"先小步验证再决定加大投入"的节奏。** 建议先批 **M0 + M1**(风险最低、拿到"零回归切换"实证),再回头决策是否继续 M2+。
4. **"对外开放北向接口"(M4)是否纳入范围。** 这是把系统真正做成"别人可调用的能力平台"的一步,属商业/产品决策,可暂缓或单独立项。
5. **标准 schema 的最终裁定人。** R2 的缓解依赖一个明确的"标准 owner",需指定。

---

## 9. 明确的边界:不做 / 暂缓什么(控制范围与预期)

为避免过度承诺和范围蔓延,以下**明确不在本期范围**:

- **不做多源联邦查询**(自动合并多个数据源的结果)。一个能力默认路由到一个实例,多源合并是真实需求出现后的后续事项,**一开始做必然过度设计**。
- **不做全量接口抽离**。只标准化"有第二数据源可能"的能力(告警/指标/CMDB/工单/日志),智观独有的深度运维动作先留在业务里。
- **不为了消除重复而重构**。消除重复是副产品,不是目标(见第 3.3)。
- **对外开放 API(M4)默认暂缓**,视商业需要单独决策。

---

## 10. 建议的启动方式(低承诺、可快速验证)

建议以**最小、最稳、收益最直接**的一步启动,做完再评估是否继续:

**第一刀:合并"数据归一"层。** 把现在散在三处的告警归一化代码,合并成一份权威的"告警标准 schema + 字段映射"。这一步:

- **风险最小**:接口调用、业务逻辑原地不动,只是把"翻译成标准字段"收到一处;
- **立刻止血**:直接根治"对话与大屏告警显示不一致"这类反复出现的线上问题;
- **产出标准的第一块实物**:合出来的 schema 就是能力契约 `alarm.query` 的返回定义,后续所有连接器对着它写。

也就是说,**不需要"先花三个月把接口全抽干净再开始"**,而是从最缠、最易出 bug 的那道归一层先撕,撕出来的第一片就是标准本身。这一步做完,"告警标准长什么样"就有了实物,再谈是否推进 M1 及后续,决策就有了扎实的落脚点。
