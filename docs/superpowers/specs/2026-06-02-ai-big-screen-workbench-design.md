# AI 大屏工坊设计方案

> 日期：2026-06-02 · 形态：产品与技术设计 · 当前阶段：实施前规格

## 背景 / 问题

客户希望普通业务用户、运维管理者，甚至不懂技术的领导，可以通过自然语言定制运维大屏，并把大屏稳定发布到 Portal 或其他系统中。

这个需求不能被简单理解为“AI 直接改 Portal 源码”或“AI 临时生成一段页面代码”。那样虽然看起来灵活，但会带来源码污染、数据不可追溯、权限不可控、版本难治理和后续维护困难。

本方案把目标定义为：

> AI 帮用户创建和持续维护一个可持久化的大屏应用资产；Portal 负责渲染、预览、发布、权限、嵌入和版本治理。

大屏不是一次性 HTML 页面，也不是 Portal 源码的一部分。它是一个独立的、可运行的业务资产，可以被保存、调整、发布、回滚、外部访问和嵌入其他系统。

## 用户定位

第一阶段面向普通业务用户和管理层用户，而不是开发者。

典型用户不需要理解前端代码、SQL、接口协议或图表配置。他们通过自然语言表达目标，例如：

- “帮我做一个领导驾驶舱，看今天告警、工单、资源利用率和重点风险。”
- “把这个告警趋势改成最近 7 天，颜色正式一点。”
- “左边加一个待处理工单，按超时时间排序。”
- “这个区域换成暖色，看起来更适合汇报。”

系统需要把这些表达转成受控的大屏配置、插件数据绑定和可渲染页面。

## 目标

1. 用户可以通过自然语言创建大屏草稿。
2. AI 可以根据用户需求选择数据插件、布局组件和视觉样式。
3. 大屏可以在 Portal 中实时预览，并支持发布为可访问链接。
4. 大屏可以作为独立应用资产持久化保存。
5. 大屏可以通过 Portal 菜单、外部链接或 iframe 被其他系统挂载。
6. 用户可以随时继续用自然语言修改已发布或草稿大屏。
7. 第一阶段支持点击组件后对话修改，后续扩展到框选和视觉圈选修改。
8. 数据来源必须可信、可追溯、有权限边界。

## 非目标

第一阶段不做：

1. AI 任意生成 React / Vue 源码并写入 Portal 仓库。
2. 普通用户直接编写 SQL 或接口脚本。
3. 任意外部数据自由接入。
4. 复杂拖拽式设计器。
5. 多人协同编辑。
6. 视觉模型圈选修改。
7. 完整低代码平台。

## 核心原则

1. **AI 生成配置，不修改 Portal 源码。**
2. **数据能力插件化，AI 负责选择、组合和配置。**
3. **大屏是长期应用资产，不是一次性页面。**
4. **非常规取数必须走受控工具链，并记录来源。**
5. **所有 AI 修改都应产出可审计、可回滚的配置 patch。**

## 总体架构

```text
+------------------+       +------------------+       +-------------------+
| 普通用户 / 领导   | <---> | AI 大屏助手       | <---> | 能力插件库         |
| 自然语言表达需求  |       | 解析/生成/修改    |       | 告警/工单/资源/... |
+------------------+       +--------+---------+       +---------+---------+
                                    |                           |
                                    v                           v
                           +------------------+       +-------------------+
                           | 大屏资产服务      | <---> | 受控数据工具链      |
                           | 草稿/版本/发布    |       | 临时取数/沉淀插件   |
                           +--------+---------+       +-------------------+
                                    |
                                    v
                           +------------------+
                           | Portal 大屏渲染器 |
                           | 预览/访问/嵌入    |
                           +------------------+
```

系统分为六个部分：

1. **AI 大屏助手**：理解用户意图，追问缺失信息，选择插件，生成大屏配置，处理修改请求。
2. **能力插件库**：封装告警、工单、资源、拓扑、容量、健康度等常用数据能力。
3. **大屏资产服务**：管理草稿、版本、发布状态、权限、分享链接和嵌入地址。
4. **Portal 大屏渲染器**：根据结构化配置渲染大屏，不执行 AI 随机生成的源码。
5. **交互式编辑层**：支持组件选择、区域选择和后续视觉圈选修改。
6. **发布与嵌入层**：支持 Portal 内部访问、外部链接访问和 iframe 挂载。

## 大屏资产模型

大屏应被建模为 `ScreenApp`，而不是普通页面文件。

```text
ScreenApp
- id
- name
- description
- owner
- status: draft / published / archived
- layout
- theme
- components
- dataBindings
- permissions
- versions
- publishTargets
- aiConversationContext
- createdAt
- updatedAt
```

### 组件模型

```text
ScreenComponent
- id
- type: metric-card / line-chart / bar-chart / table / topology / map / text / group
- title
- description
- layoutPosition
- pluginId
- queryParams
- visualConfig
- refreshInterval
- interactions
```

### 数据绑定模型

```text
DataBinding
- id
- componentId
- pluginId
- input
- outputMapping
- refreshPolicy
- cachePolicy
- permissionScope
- sourceDescription
```

### 版本模型

```text
ScreenVersion
- versionId
- screenId
- configSnapshot
- changeSummary
- changedBy
- changedByAi: true / false
- createdAt
- basedOnVersionId
```

每次 AI 修改都生成一个版本。用户可以回滚到历史版本，也可以对历史版本继续修改。

## 能力插件库

常用运维数据应提前封装为插件。插件不是前端组件，而是数据、指标或动作能力。

第一阶段建议准备 8 到 12 个核心插件：

- 今日告警总览
- 告警等级分布
- P1 / P2 告警趋势
- 待处理工单
- 工单超时风险
- 主机资源利用率 TopN
- 网络设备健康度
- 数据库资源利用率
- 重点系统健康度
- 地市 / 机房资源分布
- 容量风险 TopN
- 拓扑影响范围

### 插件协议

```text
ScreenDataPlugin
- id
- name
- domain: alarm / workorder / resource / topology / capacity / health
- description
- inputSchema
- outputSchema
- supportedVisuals
- permissionScope
- cachePolicy
- refreshPolicy
- examplePrompts
- dataSource
- owner
```

插件需要声明它能被哪些图表消费。例如告警趋势插件可以支持折线图、柱状图和面积图；待处理工单插件可以支持表格、数字卡片和 TopN 列表。

## 非常规数据处理

用户提出插件库暂时不支持的需求时，AI 可以通过受控工具链探索数据，但必须满足以下边界：

1. AI 不能编造指标。
2. 必须记录数据来源、查询条件和刷新方式。
3. 必须经过权限校验。
4. 临时数据绑定应标记为 `experimental` 或 `temporary`。
5. 高频使用的临时取数逻辑应沉淀成正式插件。
6. 如果取数涉及高风险操作或敏感数据，需要用户确认或管理员审批。

推荐流程：

```text
用户提出非常规数据需求
-> AI 判断插件库未覆盖
-> AI 通过受控工具链查询可用数据源
-> 生成临时数据绑定
-> Portal 预览
-> 用户确认
-> 后续沉淀为正式数据插件
```

## AI 生成流程

创建大屏：

```text
用户描述需求
-> AI 解析场景、角色、指标、展示目的
-> AI 判断是否需要追问
-> AI 匹配数据插件
-> AI 选择布局和组件
-> AI 生成 ScreenApp 配置草稿
-> Portal 渲染预览
-> 用户继续修改或发布
```

AI 输出必须是结构化配置，而不是自由代码。

### AI 追问策略

当缺少关键信息时，AI 需要用少量问题补齐，不应一次性问太多。

优先追问：

- 大屏用途：领导汇报、值班监控、专题分析、日常运营。
- 时间范围：今天、最近 7 天、最近 30 天、实时。
- 关注对象：全局、某系统、某地市、某机房、某业务线。
- 发布范围：仅自己可见、团队可见、内部公开、外部临时链接。

## AI 修改流程

第一阶段采用“点击组件 + 自然语言修改”。

```text
用户点击组件
-> Portal 记录 selectedComponentId
-> 用户输入修改诉求
-> AI 读取当前 ScreenApp 配置和组件上下文
-> AI 生成配置 patch
-> Portal 应用 patch 并局部预览
-> 用户确认保存为新版本
```

修改请求示例：

- “这个图换成柱状图。”
- “颜色暖一点。”
- “只看最近 7 天。”
- “这里加一个同比。”
- “把标题改成今日重点风险。”

### 配置 patch 约束

AI 修改不应直接覆盖完整配置，优先输出 patch：

```text
ScreenPatch
- targetScreenId
- baseVersionId
- operations
- summary
- riskLevel
```

操作示例：

```text
operations
- update component visualConfig
- update component title
- replace plugin binding
- add component
- remove component
- move component
```

Portal 应在应用 patch 前校验：

- 组件是否存在。
- 插件是否可用。
- 参数是否符合 schema。
- 权限是否满足。
- 布局是否冲突。

## 框选和圈选演进

第一阶段只做点击组件。

第二阶段支持框选区域：

```text
用户框选一块区域
-> Portal 根据坐标识别区域内组件
-> AI 接收 selectedComponentIds
-> AI 生成多组件 patch
```

第三阶段支持视觉圈选：

```text
用户在截图上圈选
-> 视觉模型识别圈选对象
-> 映射到 ScreenComponent
-> AI 生成 patch
```

视觉圈选体验最好，但实现复杂度高，依赖截图识别、组件映射和误识别兜底，不进入第一阶段。

## Portal 渲染器

Portal 大屏渲染器负责把 `ScreenApp` 配置渲染为大屏。

渲染器职责：

1. 解析布局。
2. 渲染组件。
3. 调用数据插件。
4. 处理刷新策略。
5. 处理加载、错误和空数据状态。
6. 支持预览模式、发布模式和嵌入模式。
7. 暴露组件选择事件，供 AI 修改流程使用。

渲染器不负责：

1. 生成业务需求。
2. 自行创造数据指标。
3. 执行未经校验的脚本。
4. 直接管理版本。

## 发布形态

大屏发布后支持多种入口：

1. Portal 内部路由：适合内部用户访问。
2. Portal 菜单挂载：适合固定成为业务页面。
3. 外部分享链接：适合领导直接打开。
4. iframe 嵌入地址：适合被其他系统挂载。
5. 临时签名链接：适合短期分享。

发布目标模型：

```text
PublishTarget
- type: portal-route / portal-menu / external-link / iframe / signed-link
- url
- visibility
- expiresAt
- createdAt
- createdBy
```

权限建议分三档：

1. 内部公开。
2. 登录后可见。
3. 签名链接或临时链接。

## MVP 范围

第一期交付最小可用闭环：

1. 大屏资产 CRUD。
2. `ScreenApp` 配置 schema。
3. `ScreenDataPlugin` 插件协议。
4. 8 到 12 个核心数据插件。
5. Portal 大屏渲染器。
6. AI 根据自然语言生成大屏配置。
7. Portal 大屏预览。
8. 点击组件后自然语言修改。
9. 配置 patch 校验。
10. 版本保存与回滚。
11. 发布链接。
12. iframe 嵌入地址。

## 实施阶段

### 阶段一：大屏资产底座

交付：

- 大屏资产服务。
- 配置 schema。
- 版本管理。
- 发布状态管理。
- Portal 预览路由。

验收：

- 可以手工创建一个配置并在 Portal 渲染。
- 可以保存多个版本并回滚。
- 可以发布并通过链接访问。

### 阶段二：插件体系

交付：

- 插件注册表。
- 插件输入输出 schema。
- 告警、工单、资源类核心插件。
- 插件权限与刷新策略。

验收：

- 大屏组件可以绑定插件数据。
- 插件输出能被数字卡片、趋势图、表格消费。
- 插件异常时 Portal 显示可理解的错误状态。

### 阶段三：AI 创建大屏

交付：

- 用户自然语言需求解析。
- 插件匹配。
- 大屏配置生成。
- 缺失信息追问。

验收：

- 用户输入一句需求后能生成可预览大屏。
- AI 不输出自由源码。
- 生成配置通过 schema 校验。

### 阶段四：AI 修改大屏

交付：

- 组件选择上下文。
- 自然语言修改入口。
- AI 生成 patch。
- Patch 校验与预览。
- 保存为新版本。

验收：

- 用户点击某个组件后，可以要求改标题、颜色、图表类型、时间范围。
- 修改失败时给出明确原因。
- 修改后可回滚。

### 阶段五：发布与外部挂载

交付：

- 外部访问链接。
- iframe 嵌入地址。
- 简单权限控制。
- 发布管理界面。

验收：

- 已发布大屏可以从 Portal 外部打开。
- 其他系统可以通过 iframe 挂载。
- 未授权用户无法访问受限大屏。

## 风险与约束

### 数据可信风险

AI 不能随意创造指标。所有指标必须来自插件、受控工具链或明确的数据源。

缓解：

- 插件注册表记录数据来源。
- 临时取数标记为 experimental。
- 发布前展示数据来源摘要。

### 权限风险

大屏可能展示敏感运维数据。

缓解：

- 数据插件声明权限范围。
- 大屏资产声明访问权限。
- 发布链接支持失效时间和签名。

### 自由度风险

如果第一阶段允许 AI 任意写代码，会导致安全和维护不可控。

缓解：

- 第一阶段只允许结构化配置。
- 自定义能力通过插件扩展，而不是直接写 Portal 源码。

### 体验风险

普通用户不懂配置，如果 AI 生成效果不好，用户需要能自然修改。

缓解：

- 支持点击组件后直接对话修改。
- 修改以 patch 方式局部应用。
- 保留版本回滚。

## 测试 / 验证

实施后需要覆盖：

1. 配置 schema 单元测试。
2. 插件输入输出契约测试。
3. 大屏渲染器组件测试。
4. AI 生成配置的结构校验测试。
5. AI patch 应用与回滚测试。
6. 发布链接访问测试。
7. iframe 嵌入 smoke 测试。
8. 权限拒绝测试。
9. 插件失败、空数据、超时状态测试。

## 结论

推荐按“AI 大屏助手 + 能力插件库 + 大屏配置资产 + Portal 大屏渲染器 + 发布/嵌入能力”的方向实施。

第一阶段不要做 AI 自由生成页面代码，也不要让 AI 直接修改 Portal 源码。应先完成配置驱动的大屏资产闭环，让普通用户能通过自然语言创建、预览、调整和发布大屏。

后续在这个稳定底座上，再逐步扩展框选修改、视觉圈选、临时数据能力沉淀和更强的外部嵌入治理。
