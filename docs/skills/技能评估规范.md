# 技能评估规范

> 适用范围：本规范适用于本仓库中各类 Skill / SKILL.md 的设计评审、测试验收、迭代优化与触发描述优化。
>
> 评估依据：本文档基于 `skill-creator` 技能的方法论整理，核心依据包括真实用户任务测试、with-skill 与 baseline 对照、人工评审、断言评分、基准聚合，以及触发准确率优化流程。

## 1. 目的

本规范用于回答三个问题：

1. 一个 Skill 是否真的解决了用户问题；
2. 一个 Skill 是否比“不用 Skill”或“旧版 Skill”更好；
3. 一个 Skill 的“更好”是否可以被复现、被验证、被解释。

Skill 评估不以“写得像不像提示词”为核心，而以“是否在真实场景下稳定地产生更好的结果”为核心。

## 2. 核心评估原则

### 2.1 以真实任务为中心

评估应基于真实用户会提出的任务，而不是抽象能力描述或过于理想化的样例。

- 测试 prompt 应尽量贴近真实表达；
- 应覆盖不同说法、信息完整度差异、边界场景；
- 应优先验证用户真正关心的最终结果，而不是中间过程是否“像我们设想的那样发生”。

**依据：** `skill-creator` 明确要求测试用例应为“真实用户会说的话”，并强调不要用过于抽象的测试题替代真实场景。

### 2.2 以对照实验为核心证据

Skill 的价值不是“它也能完成任务”，而是“它能比 baseline 更稳定、更高质量或更高效率地完成任务”。

- 新建 Skill 时，baseline 为 **不用 Skill**；
- 迭代已有 Skill 时，baseline 为 **旧版 Skill** 或上一版稳定版本；
- 所有关键结论应尽量来自对照，而不是单次体验。

**依据：** `skill-creator` 要求每个 eval 在同一轮中同时执行 with-skill 与 baseline 版本，以便做同步对比。

### 2.3 以定性与定量结合为准

Skill 评估不能只看主观观感，也不能只看数字。

- **定性评估**：关注输出是否真正可用、是否符合用户意图；
- **定量评估**：关注 assertions、通过率、时延、token 成本等客观指标；
- 二者结合后，才能判断一个 Skill 是否值得长期保留与推广。

**依据：** `skill-creator` 要求在人工查看输出的同时，补充 assertions、grading 和 benchmark 聚合。

### 2.4 以泛化能力而非样题命中为目标

Skill 不是为了通过少数样例而设计，而是为了能够长期复用。

- 不得为了某几个例子堆叠过度僵硬的规则；
- 对反馈的修正应尽量抽象出共性原因；
- 优化后应再次通过不同表达方式进行验证，避免“修一个样例坏一片场景”。

**依据：** `skill-creator` 明确强调要避免 overfit，应从用户反馈中提炼一般性规律，而不是只修补个别样题。

### 2.5 以最小惊讶原则为底线

Skill 的行为应与其描述一致，不应产生超出用户预期的副作用，更不得包含恶意、误导、越权或破坏性内容。

**依据：** `skill-creator` 的 `Principle of Lack of Surprise` 明确要求 Skill 内容和行为不得让用户意外，更不能用于恶意用途。

## 3. 评估依据总览

Skill 评估主要基于以下六类证据：

### 3.1 用户意图与目标定义

用于判定：这个 Skill 要解决什么问题、在什么场景触发、产出什么结果。

**证据来源：**
- 用户需求澄清；
- SKILL.md 中的 description；
- 输出格式约定；
- 任务目标说明。

### 3.2 真实测试用例

用于判定：Skill 在真实 prompt 下是否有效。

**证据来源：**
- `evals/evals.json`；
- prompt、输入文件、expected_output；
- 典型场景与边界场景覆盖情况。

### 3.3 基线对照结果

用于判定：Skill 是否真正带来增益。

**证据来源：**
- `with_skill/` 输出；
- `without_skill/` 或 `old_skill/` 输出；
- benchmark 中的 delta 信息。

### 3.4 客观断言与评分

用于判定：可验证部分是否满足明确标准。

**证据来源：**
- assertions；
- `grading.json`；
- 程序化校验脚本；
- benchmark 中的 pass rate。

### 3.5 运行成本与执行轨迹

用于判定：Skill 是否带来不合理的时间或 token 开销，是否诱导模型做无效工作。

**证据来源：**
- `timing.json`；
- benchmark 的 duration / tokens 统计；
- 执行 transcript。

### 3.6 触发准确率测试

用于判定：这个 Skill 是否该触发时能触发，不该触发时不会误触发。

**证据来源：**
- 触发评估 query 集；
- should-trigger / should-not-trigger 标注；
- 训练/测试集结果；
- 多次重复运行的触发率统计。

## 4. 评估维度与判定标准

| 维度 | 核心问题 | 评估方式 | 判定标准 | 主要依据 |
|---|---|---|---|---|
| 任务完成度 | 是否完成用户真正想做的事 | 人工评审、对照 expected_output | 核心目标完成，无关键遗漏 | 用户意图、输出结果 |
| 输出质量 | 输出是否可用、清晰、贴合场景 | 人工评审 | 可直接使用或仅需轻微修改 | review 反馈、产出文件 |
| 格式遵循度 | 是否遵守约定的结构与模板 | 断言 + 人工检查 | 关键格式项齐全 | output format、grading |
| 客观正确性 | 可验证内容是否正确 | assertions、脚本校验 | 关键断言通过率达标 | grading、benchmark |
| 相对增益 | 是否优于不用 Skill 或旧版 Skill | 对照评测 | 至少在质量、稳定性或效率上有明确提升 | baseline 对照、delta |
| 稳定性 | 同类任务下是否稳定 | 多 eval 汇总分析 | 不出现明显偶发性失效 | benchmark、analyzer |
| 泛化能力 | 是否只对样题有效 | 多样化 prompt 复测 | 不依赖单一措辞，不因小变体失效 | eval 集、反馈迭代 |
| 效率成本 | 是否带来过高时延与 token 开销 | timing / benchmark | 成本上涨需能换来明确收益 | timing、tokens |
| 触发准确率 | 是否正确触发和避免误触发 | trigger eval | 正负样本表现合理 | trigger 测试结果 |
| 安全与可预期性 | 是否有越权、误导或让用户意外的行为 | 内容审查、输出审查 | 不越界、不误导、行为与描述一致 | Skill 内容、输出行为 |
| 可维护性 | Skill 是否清晰、不过度臃肿 | 文档结构审查 | 层次清晰，说明充分，资源拆分合理 | SKILL.md、references、scripts |
| 可复用性 | 是否沉淀了可重复使用能力 | 过程回顾 | 共性步骤被抽象为资源或脚本 | transcript、scripts |

## 5. 各维度的详细解释

### 5.1 任务完成度

任务完成度回答的是：“用户要的结果，最终有没有交付出来？”

重点看：

- 是否完成了用户的核心目标；
- 是否遗漏关键步骤；
- 是否输出了表面上很多内容，但真正要交付的结果并未形成。

这是第一优先级指标。若核心任务未完成，其他指标即使表现良好，也不能判定 Skill 合格。

### 5.2 输出质量

输出质量回答的是：“结果好不好用？”

重点看：

- 是否清晰、贴题、可直接消费；
- 是否符合用户工作语境；
- 是否需要大量返工才能落地。

主观型 Skill（如文风、创意、设计建议）尤其应重视此项。

### 5.3 格式遵循度

对于报告模板、结构化 JSON、指定目录产物等任务，Skill 需要遵守明确格式。

重点看：

- 标题、章节、字段是否齐全；
- 文件名、路径、结构是否符合要求；
- 是否存在“内容有了，但格式错了，导致不能直接用”的情况。

### 5.4 客观正确性

对于可验证任务，必须尽量把“好不好”转化成“是否满足清晰断言”。

适用场景包括：

- 文件转换；
- 数据抽取；
- 代码生成；
- 固定结构文档输出；
- 多步流程执行结果检查。

重点看：

- 关键字段是否存在；
- 结果是否满足规则；
- 程序化可检查内容是否通过。

> 注意：对纯主观型任务，不应为了“量化而量化”，不要堆砌缺乏意义的伪断言。

### 5.5 相对增益

相对增益回答的是：“为什么要有这个 Skill？”

重点看：

- 与 baseline 相比，质量是否更高；
- 是否更稳定；
- 是否减少用户反复澄清与返工；
- 是否节约时间或 token；
- 若成本更高，是否换来了明显收益。

如果 Skill 只是让流程更复杂，但对最终结果没有实质提升，则不应判定为高价值 Skill。

### 5.6 稳定性

稳定性回答的是：“这个 Skill 是偶然成功，还是稳定可用？”

重点看：

- 同类任务下结果是否波动过大；
- 是否存在某一两个样例表现好、其他样例频繁失效；
- assertions 是否高度不稳定。

高波动通常意味着：

- 指令过于模糊；
- 对输入前提依赖过强；
- 关键行为没有被稳定约束；
- Skill 长度或组织方式导致模型执行不一致。

### 5.7 泛化能力

泛化能力回答的是：“换个说法、换个边界条件，还能不能用？”

重点看：

- 不同措辞是否都能完成任务；
- 信息更少、更口语化、更混乱时能否保持较好表现；
- 是否对少数样题过拟合。

Skill 优化应优先提炼共性原则，而不是给每个样题单独补规则。

### 5.8 效率成本

效率成本回答的是：“这个 Skill 值不值得这份开销？”

重点看：

- 执行耗时是否明显变长；
- token 消耗是否显著增多；
- 增加的成本是否带来可靠收益；
- transcript 中是否存在大段无效探索、重复生成、反复自证。

如果 Skill 把模型引向大量无效工作，应优先做减法，收紧无价值步骤。

### 5.9 触发准确率

触发准确率回答的是：“这个 Skill 会不会被正确选中？”

重点看：

- should-trigger 样例是否被触发；
- should-not-trigger 样例是否不会误触发；
- 边界样例是否表现合理。

触发准确率评估的对象不是 Skill 主体能力，而是 `description` 等元信息对路由的帮助程度。

### 5.10 安全与可预期性

这是底线维度，不做加分，只做否决。

重点看：

- Skill 内容是否诱导越权、欺骗、误导；
- 是否可能执行与用户预期明显不符的动作；
- 是否存在安全、合规、权限边界问题；
- Skill 声明与实际行为是否一致。

如触及底线，应直接判定不通过。

### 5.11 可维护性

可维护性回答的是：“这个 Skill 将来还好改吗？”

重点看：

- SKILL.md 结构是否清楚；
- 是否遵循渐进披露，避免把所有内容都堆在单文件里；
- references、scripts、assets 是否拆分合理；
- 说明是否解释了“为什么这样做”，而不只是堆砌命令式要求。

### 5.12 可复用性

可复用性回答的是：“运行几次之后，有没有沉淀出稳定能力？”

重点看：

- 多个测试中是否重复出现相同步骤；
- 这些共性操作是否已经下沉为脚本或参考文档；
- 是否减少未来调用时的重复造轮子。

## 6. 不同类型 Skill 的评估侧重

### 6.1 客观型 Skill

典型例子：

- 表格/文档处理；
- 数据转换与提取；
- 代码生成与修改；
- 固定格式报告；
- 脚本化工作流。

评估重点：

- assertions 设计是否充分；
- baseline 对照是否明显；
- pass rate 是否提升；
- time / token 成本是否合理；
- 是否能尽量程序化验证。

### 6.2 主观型 Skill

典型例子：

- 文案润色；
- 风格生成；
- 设计建议；
- 创意型产出；
- 表达方式优化。

评估重点：

- 人工 review；
- 用户满意度；
- 输出是否稳定、自然、贴合场景；
- 是否能解释清楚策略背后的原因。

对于此类 Skill，定量指标更多起辅助作用，不能代替人工判断。

## 7. 推荐评估流程

### 7.1 明确目标与输出

在评估前，需要先说明：

- Skill 解决什么问题；
- 什么场景下应触发；
- 输出形式是什么；
- 什么结果算成功。

### 7.2 设计真实 eval 集

至少准备 2~3 个真实测试 prompt，并尽量覆盖：

- 典型场景；
- 不同表达方式；
- 近邻边界场景；
- 可能的失败点。

### 7.3 同步执行 with-skill 与 baseline

同一轮测试中，必须同时拿到两组结果：

- with-skill；
- without-skill / old-skill。

避免不同时间、不同上下文导致结果不可比。

### 7.4 补充 assertions

在运行过程中或结果初步产出后，为可验证项补充断言：

- 断言名称要清晰；
- 断言应可重复验证；
- 能程序化就尽量程序化；
- 主观项不强行量化。

### 7.5 评分与聚合 benchmark

至少统计以下指标：

- pass rate；
- duration；
- tokens；
- 每个 eval 的分项表现；
- with-skill 与 baseline 的差值。

### 7.6 人工审阅输出

人审重点看：

- 结果是否真的可交付；
- 是否符合用户使用习惯；
- 哪些问题 benchmark 看不出来，但人一眼就能发现。

### 7.7 分析与迭代

优先解决以下问题：

1. 核心任务未完成；
2. 触发错误或边界不清；
3. 成本明显上升但收益不成立；
4. 对个别样例有效但不具备泛化能力；
5. 存在重复劳动但尚未沉淀为脚本/资源。

## 8. 验收门槛

### 8.1 必过项

以下任一项不满足，则 Skill 不通过：

- 存在安全、越权、恶意或误导性行为；
- 核心任务无法完成；
- 与 baseline 相比没有实质增益；
- 输出明显不可用；
- 触发逻辑严重失真；
- description 与实际行为明显不一致。

### 8.2 建议达标项

以下项目用于判断 Skill 是否达到“可推广使用”水平：

- 关键 assertions 通过率较高；
- 多个 eval 下表现稳定；
- 成本增加具有明确收益支撑；
- 触发准确率较好；
- SKILL.md 结构清晰、说明充分；
- 重复操作已尽量固化为脚本或参考资源。

## 10. 与仓库现有写作规范的关系

本文档关注“如何评估一个 Skill 是否有效”，与 [`SKILL_AUTHORING.md`](./SKILL_AUTHORING.md) 互补：

- `SKILL_AUTHORING.md` 重点约束 **Skill 怎么写**；
- 本文档重点约束 **Skill 写完后怎么评估、怎么验收、为什么这样评估**。

建议在以下场景同时参考两者：

1. 新建 Skill：先按写作规范起草，再按本规范设计评估；
2. 迭代 Skill：先用本规范定位问题，再回到写作规范修正文档结构与边界说明；
3. 触发优化：在本规范中看触发准确率要求，在写作规范中落实到 description 与边界声明。

## 11. 一句话结论

一个好的 Skill，不是“写得像一个 Skill”，而是：

- 该触发时能触发；
- 触发后能完成真实任务；
- 相比 baseline 有可证明的增益；
- 增益能被定性与定量证据共同支撑；
- 不因少数样题过拟合；
- 不做任何让用户意外的事。
